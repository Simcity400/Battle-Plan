# the game Map 3D Objects Replay Plan

## Executive summary

Static on-map objects in the game are not a single data source. They are
a blend of text locators/rules, text entity definitions, standard texture files,
and binary Paradox mesh assets:

- Object placement and rules are mostly text and cheaply catalogable:
  `map/buildings.txt`, `map/cities.txt`, `map/ambient_object.txt`,
  `map/supply_nodes.txt`, `map/railways.txt`, `common/buildings/*.txt`, and
  `gfx/entities/*.gfx` / `*.asset`.
- Visual geometry is not cheaply reproducible from text alone. The final meshes
  are `.mesh` files under `gfx/models/`, and sampled files use a binary
  `pdxasset`-style format with embedded section names and binary payloads. They
  are byte-readable, but not directly parseable without a dedicated mesh decoder
  or engine-captured draw inputs.
- Buildings, cities, ports, airfields, supply hubs, landmarks, and ambient
  objects should therefore be handled first as a grounded object manifest, then
  rendered only after either a real D3D11 `map_objects_pass` is captured or a
  real `.mesh` importer/material path exists.
- 2026-07-09 product-surface update: `replay_app` blocks
  `--buildings-from-files` and `--buildings-preview-all`, and the former flat
  screen-space preview module has been removed from the app. Object decoding can
  continue in tooling, but visible map objects must enter the product renderer
  through `map_objects_pass` or a real mesh/material importer with validation.
- Unit/division counters are a different class. They are billboarded UI-like
  sprites and text sourced from `interface/mapicons.gui`,
  `interface/mapicons.gfx`, `interface/subuniticons.gfx`, and
  `interface/texticons.gfx`, driven by replay division state. They should be
  generated by the replay UI/map overlay path, not by the static 3D mesh object
  path.

Recommended sequencing: build a data-only map-object manifest; implement
division counters from interface assets and replay state; then run a future
capture-discovery pass for static map-object draw calls. Do not fabricate
stand-in meshes, city scatter, or blocky markers at locators.

## Existing replay constraints

The replay project requires a full-game replay interface, not a summary
dashboard. `documents/DESIGN.md` says the replay app must reconstruct the map
and UI from extracted state and real game assets, with no fabricated colors,
icons, fonts, or layouts.

The current map renderer is already organized around grounded production passes:

- `replay_interface/documents/MAP_REPLICA_PLAN.md:14-34` lists the map source
  families already treated as source of truth, including `map/buildings.txt`,
  `map/railways.txt`, `map/supply_nodes.txt`, `map/unitstacks.txt`,
  `map/ambient_object.txt`, `map/weatherpositions.txt`, `map/positions.txt`,
  `gfx/entities/*.gfx`, `gfx/entities/*.asset`, and `common/buildings/*.txt`.
- `replay_interface/documents/MAP_REPLICA_PLAN.md:35-52` requires each map
  renderer step to be tied to named the game source files or captured runtime
  payloads, with documented blockers instead of guesses.
- `replay_interface/documents/MAP_REPLICA_PLAN.md:76-90` already classifies
  trees, cities, and static objects as source-cataloged but not rendered.
- `replay_interface/documents/MAP_REPLICA_PLAN.md:163-170` explicitly calls 3D
  map objects a full entity-mesh render system and defers them past the first UI
  phase.
- `replay_interface/native/map_viewer/src/pass_graph.rs:5-14` has pass kinds for
  `Terrain`, `Water`, `Rivers`, `Borders`, `Trees`, `Cities`, and `Overlays`.
- `replay_interface/native/map_viewer/src/pass_graph.rs:54-76` blocks cities and
  overlays unless the renderer has named D3D11 bundles or proven generated
  placement/entity data.
- `replay_interface/native/terrain_capture/README.md:20-25` says water, rivers,
  borders, and trees are captured only behind strict shader-family gates, while
  cities and overlays remain deferred until equivalent signatures exist.
- `replay_interface/native/terrain_capture/README.md:50-65` defines the existing
  pass-advance model: each moment is accepted only when the active pixel shader
  proves the matching vanilla shader family and the required resources are
  present.
- `replay_interface/native/terrain_capture/README.md:92-117` lists the bundle
  payload classes already captured for map passes: session metadata, frame
  bundle, input assembler buffers, shader bytecode, constant buffers, SRVs,
  output-merger descriptors, and source evidence.
- `replay_interface/native/terrain_capture/src/d3d11_runtime.rs:88-117`
  contains named bundle files and capture moments for terrain, water, rivers,
  borders, trees, and UI, but no cities or map-objects bundle.
- `replay_interface/native/terrain_capture/src/d3d11_runtime.rs:315-410`
  contains capture profiles for terrain, terrain chunks, water, rivers, borders,
  and trees only.
- `replay_interface/native/terrain_capture/src/d3d11_runtime.rs:6714-6828`
  rejects unsupported map-frame moments outside those known terrain-family
  passes.

This plan keeps that fail-closed model. Static 3D objects are not eligible for
rendering until the replay has either captured their real D3D11 draw sequence or
implemented a grounded `.mesh` and material importer.

## Static object rendering options

### Option A: capture and replay a map-objects pass

This matches the existing terrain/rivers/trees architecture. The replay would
capture the exact D3D11 draw inputs for map objects and replay them as a
production map-scene pass.

Why this is attractive:

- It avoids reverse-engineering `.mesh`, `.anim`, material, particle, LOD,
  culling, snow, fog, lighting, and nudging behavior up front.
- It follows the existing captured-pass pattern where terrain-like layers record
  shader bytecode, input layout, buffers, constant buffers, SRVs, samplers,
  output-merger state, and render-target payloads.
- It can preserve visual parity for close-zoom objects without inventing
  geometry or materials.

Why it is not ready today:

- There is no grounded shader/resource signature for cities, buildings, or
  entity meshes in `terrain_capture`.
- Current runtime code knows how to validate terrain, water, rivers, borders,
  and trees, but not a static object family.
- Capturing one camera window may not be enough if the replay needs arbitrary
  map panning and zooming. A pass capture can replay what the engine drew in
  the captured camera state; it is not automatically a complete world object
  library.

Recommended position: use capture discovery first. Promote to production only
after a stable map-object draw family is identified and validated.

### Option B: generated inputs from shipped data

This can produce object manifests and UI counters, but not full static 3D
objects by itself.

Cheap and grounded:

- Parse `map/buildings.txt` into typed object slots.
- Parse `common/buildings/*.txt` into map-display rules, spawn points,
  `show_on_map`, `show_on_map_meshes`, and always-shown flags.
- Parse `gfx/entities/*.gfx` and `*.asset` into entity-to-mesh references,
  scales, states, locator names, particle names, and material texture
  references.
- Join replay building levels from extracted state to candidate slots.
- Generate unit/division counters from interface sprites and replay division
  state.

Not cheap or currently grounded:

- Converting `.mesh` files into vertex/index/material data.
- Matching engine material shaders such as `PdxMeshAdvanced` and
  `PdxMeshAdvancedSnow`.
- Matching object LOD, sorting, depth behavior, seasonal/snow material variants,
  damage/burning particle states, and engine nudging rules.
- Recreating city scatter from `cities.bmp` and `cities.txt` with confidence
  equal to the game.

Recommended position: use generated data for manifests and counters now; do not
use it to fabricate visible 3D buildings/cities.

### Option C: mesh import

A future `.mesh` importer could eventually make static 3D object replay
independent of camera-window D3D captures. It would need:

- A documented parser for Paradox `.mesh` sections and payloads.
- Static mesh extraction: vertex/index streams, vertex declarations, materials,
  texture references, bounding volumes, and LODs.
- Material reproduction for the shader families used by buildings, landmarks,
  cities, and supply objects.
- Optional animation and particle support for damaged, burning, idle, and
  special states.
- Validation against captured D3D11 object draws, because a parser alone does
  not guarantee render parity.

This is a substantial reverse-engineering project. It should remain behind the
capture-discovery path unless capture cannot provide enough coverage.

## Proposed `map_objects_pass` capture moment

The pass should not be added as a broad "anything after terrain" profile. It
must have the same fail-closed standard as rivers and trees.

### Name

`map_objects_pass`

If discovery shows cities and buildings are distinct stable draw families, split
later into `cities_pass` and `buildings_pass`. Do not split before evidence.

### Scope

Static or semi-static 3D world objects drawn into the map-scene render target:

- City meshes and generated city clusters.
- State and province building meshes.
- Ports, dockyards, naval bases, airfields, supply hubs, refineries, reactors,
  radar, bunkers, coastal bunkers, landmarks, dams, locks, and facilities.
- Ambient objects if they share the same object/entity mesh draw family.

Out of scope:

- Unit/division counters.
- UI widgets.
- Text labels.
- Map-mode icons rendered as UI overlays.
- Actual animated unit models unless future evidence shows they share the same
  object pass and the replay product explicitly needs them.

### Open conditions

Minimum hard requirements:

- A valid `terrain_active_pass` has already been accepted for the frame.
- The draw is still targeting the map-scene render/depth target, not the
  swapchain/backbuffer UI target.
- Input assembler state is non-empty and contains a mesh-like vertex/index
  stream, not the known terrain chunk layout.
- Active shaders are not any already-known terrain, water, river, border, or
  tree shader family.
- Output-merger state, depth state, viewport, and render-target dimensions are
  compatible with the current map-scene sequence.

Promotion requirements before accepting as production:

- Shader bytecode/reflection or source evidence identifies a stable entity,
  mesh, city, or object material family.
- Bound SRVs and material textures can be tied to shipped `gfx/models` /
  `gfx/entities` sources by path, hash, or repeatable resource identity.
- The draw sequence appears after terrain/water/rivers/trees and before UI in
  repeated frames.
- Captured pre/post render-target payloads prove the sequence visibly accounts
  for static map objects.

Forbidden open conditions:

- "First unknown draw after terrain."
- "Any draw using depth."
- "Any draw before UI."
- A guessed slot list with no shader/resource evidence.

### Record payload

For each accepted object sequence, record at least:

- `capture_moment = "map_objects_pass"`.
- Frame/camera metadata and map projection constants.
- Draw order and draw arguments.
- Primitive topology.
- Input layout descriptors.
- Vertex buffers, index buffers, offsets, strides, and referenced byte ranges.
- Vertex shader and pixel shader bytecode plus reflection where available.
- VS/PS constant buffers and dirty ranges.
- PS SRVs with texture payloads, dimensions, formats, hashes, and source-path
  evidence where known.
- Sampler state.
- Rasterizer, blend, depth-stencil, viewport, and scissor state.
- Output-merger render target and depth-stencil descriptors.
- Pre-pass and post-pass render-target/depth payloads or a documented reason
  if a payload is intentionally omitted.
- Optional source classification linking draws to candidate entity/mesh names
  from `gfx/entities` or `gfx/models`.

### Close conditions

Close the pass when one of these is proven:

- The renderer transitions to the UI/backbuffer target.
- The next known non-object map layer or UI pass begins.
- Present occurs.
- A repeated-frame heuristic proves the object sequence ended without entering
  UI, and the captured post-pass target is stable across equivalent camera
  frames.

### Validation

The production renderer should replay `map_objects_pass` into the same
map-scene color/depth target used by terrain and compare against the captured
post-pass payload. A pass is not accepted because it merely "looks plausible."

If no stable shader/resource identity can be found, keep `map_objects_pass`
rejected and leave cities/buildings documented as blockers.

## Unit/division counters

Unit counters are not static 3D objects.

Evidence:

- `interface/mapicons.gui:17-187` defines the on-map `unit_counter` as a UI
  container with sprites, text, bars, flags, overlays, and status icons.
- `interface/mapicons.gfx:37-83` defines the counter background/overlay sprites.
- `interface/subuniticons.gfx:1-180` defines category sprites such as infantry,
  motorized, armor, and support categories.
- `interface/texticons.gfx:513-641` defines small NATO symbol sprites.
- `map/unitstacks.txt` provides static map-space unit-stack locators, but live
  division state must come from replay extraction.
- `extractor/documents/MASTER_EXTRACTION_CONTRACT.md:76-83` says
  `divisions_live` production data already includes identity, location,
  movement, org, strength, and related live division fields.

Recommended strategy:

1. Treat counters as a map overlay rendered by replay UI code, aligned to the
   map camera and projection.
2. Use real interface assets and GUI layout data, not custom counter art.
3. Drive visible fields from replay division state: controller flag, type/NATO
   icon, stack count, organization, strength, supply/attrition/order status, HQ
   badge, selection state, and other fields as extraction allows.
4. Validate against captured `ui_pass` or screenshots when available.
5. Do not wait for `.mesh` import. Counters can be replayed from parseable UI
   definitions and live division data.

If later evidence shows the game renders counters in a dedicated 3D/overlay
pass before final UI composition, that should become a dedicated
`unit_counters_pass`, not part of `map_objects_pass`.

## No-fabrication implications

Until extraction or capture provides the missing pieces, the replay must not:

- Draw placeholder cubes, billboards, or icons for factories, ports, cities,
  supply hubs, or landmarks and call them map objects.
- Scatter city meshes directly from `cities.bmp` unless the engine scatter
  algorithm has been reproduced or captured.
- Assume `.mesh` vertex/index layouts from sampled bytes.
- Infer runtime building existence solely from `map/buildings.txt`; those rows
  are slots/locators, not built-state truth.
- Use state-history files as live replay state except as scenario examples.
- Treat one captured camera window as a complete world object dataset without a
  coverage plan.
- Merge UI counters into the static 3D object pass.

Acceptable interim output:

- Object manifests with exact source paths, locators, candidate entities,
  referenced meshes, and missing render reasons.
- Gap badges or debug overlays that explicitly say object rendering is blocked
  by missing captured pass or missing mesh importer.
- UI-like division counters generated from real interface assets and replay
  state.

## Ordered implementation roadmap

1. Build a data-only map-object manifest.
   - Parse `map/buildings.txt`, `map/cities.txt`, `map/ambient_object.txt`,
     `map/supply_nodes.txt`, `map/railways.txt`, `common/buildings/*.txt`,
     `gfx/entities/buildings.gfx`, `gfx/entities/buildings.asset`,
     `gfx/entities/landmarks.gfx`, and `gfx/entities/landmarks.asset`.
   - Preserve referenced mesh paths, material texture paths, entity names,
     spawn-point names, slot coordinates, rotations, province ids, state ids,
     and rule flags.
   - Join actual replay building levels from extracted state, but keep slot
     locators and live existence separate.

2. Implement unit/division counters as a replay overlay.
   - Use `interface/mapicons.gui`, `interface/mapicons.gfx`,
     `interface/subuniticons.gfx`, and `interface/texticons.gfx`.
   - Project division positions from replay state and locator/province data.
   - Render org/strength bars, count text, type/NATO icons, flags, order and
     supply status, and selection states as extraction supports.
   - Validate against `ui_pass` or reference screenshots.

3. Run future capture discovery for static object draws.
   - In a real the game session, inspect draws after accepted terrain-family passes
     and before UI.
   - Log shader bytecode hashes, reflection, input layouts, SRV texture names or
     hashes, OM targets, depth state, and pre/post target deltas.
   - Look specifically for entity/mesh material families and texture bindings
     that match `gfx/entities` and `gfx/models` sources.

4. If discovery finds a stable family, add `map_objects_pass`.
   - Add a gated capture profile, bundle file, validator, and map-viewer replay
     path.
   - Record exact draw payloads and output-merger state.
   - Diff replay output against captured post-pass targets.
   - Decide whether a camera-window pass is enough for product needs or whether
     object coverage requires panning/capture-library work.

5. If capture cannot provide enough coverage, design a `.mesh` importer.
   - Reverse-engineer and document the `.mesh` section format.
   - Extract vertices, indices, materials, textures, LODs, and bounds.
   - Implement the smallest static subset first: one city mesh, one factory,
     one naval base, one supply station, and one landmark.
   - Validate every imported object class against captured draw evidence.

6. Add dynamic object states only after the static path is real.
   - Damage, construction, burning, destroyed landmarks, level variants,
     naval-base/dockyard growth, snow/season materials, and particles should be
     separate acceptance items.

7. Add coverage QA.
   - Use close-zoom comparison scenes over dense city areas, major ports,
     airfields, factories, supply hubs, landmarks, bunkers, and rail/logistics
     areas.
   - Track each missing class as a documented blocker until capture/import
     evidence exists.

## Bottom line

Map-object data can be cataloged now, unit counters can be generated from real
UI assets and live replay state, but static 3D buildings/cities/ports should
remain deferred until a grounded object pass or a real Paradox mesh importer
exists. The safest next product-visible work is unit counters; the safest next
static-object work is a manifest plus capture discovery, not visible rendering.
