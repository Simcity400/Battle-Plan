# Identify a recording target by process identity and state

Windows can reuse a process ID. Discovery records the process creation time with the ID, and opening a selected target rechecks both. Creation time comes from the system process list and agrees with `GetProcessTimes`. The syscall fills an aligned buffer with process and thread rows. An absent target is treated as exited. If access is denied when checking status, thread state is the remaining evidence. The live game selector excludes exiting processes and frozen processes, including threads suspended for Windows Error Reporting. A process with a blocked thread that is waiting for a reason other than suspension can still run. If several games are running, discovery waits for a unique target. Once recording has started, it reports changes in the set of other live games without switching targets. A recorded process can still be listed after it stops being a candidate for a new recording.

The recorder and desktop app share the recordings folder default. The platform crate resolves Windows registry and environment defaults, while the recorder owns capture and finalization policy. A session-scoped named mutex treats a more privileged holder as a refusal. A failed claim cannot keep the name occupied. Windows module exports can be forwarded to a different module, so address resolution uses the module that actually owns the export.

The one-shot comparison reader requests read-only access and refuses partial copies. Its addresses describe the other process, so local cache hints have no meaning. Tests that need a child process use a different image name from the game so a running recorder never selects the fixture. The suspension test waits for a context read because the request to suspend by itself does not guarantee that the thread has stopped.

`game_processes_named` borrows the aligned system listing as process entries linked by `NextEntryOffset`. Each entry is followed by the `NumberOfThreads` thread rows reported by the system. The listing stays alive while those entries and rows are read. `Event` can be shared and moved between threads because a Windows event handle may be signalled, reset and waited on from any thread. Its owned handle closes on drop.
