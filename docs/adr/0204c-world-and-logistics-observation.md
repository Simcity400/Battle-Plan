# 0204-C. Use the admitted world occurrence and certify balance cells independently

Native world invalidation identifies a change in the world, even when the attempted load does not succeed. The next readable hourly boundary admits the new occurrence and starts with a partial observer interval. Generation exhaustion and concurrent invalidations leave the attachment closed. Waiting for native writers or guessing their order would let an old occurrence admit new observations. The state and adjacency reload scopes invalidate both before and after work, so an hourly boundary during either scope admits none of its changes. World destruction hands off to the original without retaining a collector return frame during the original's unwind.

Logistics balance capture keeps the available-stock operand of the native balance write. Existing supply or convoy values cannot reconstruct a value for a cell the observer has never seen. Repeated writes are tracked per country history and archetype. An overlapping write, unreadable operand or owner-history change withdraws only that cell until its next clean write. An unidentified store withdraws all cells it might have reached. A writer that stores nothing because its index is beyond the bounds does not withdraw a cell. The store test keeps the game's signed-index behavior, including negative indices.

Observation enters its epoch and cell stamps before the native store. The readers wait for a matching, settled stamp, and a write publishes only if it completes without contention or a session change. The last writer clears transient contention without certifying a cell. If an unwind provides no explicit refusal, it leaves the cell uncertified with the unwind reason. The callback binds to both current and staged storage because publication may race entry. Linking pending storage before testing for active callbacks prevents a missed write. Published storage stays stable until callbacks quiesce, and a load starts a new occurrence rather than adopting the previous storage.

Both modules' `Hooks::new` require the memory source and base of the authenticated executable. The family owner is exclusive and restores the hooks and drains native execution before releasing their code. The logistics `release` also requires every reader to have finished because the retained heap storage is cleared on detach.
