# 0001. Build one installer for each release and promote it to its channel

The recorder and desktop app ship together at the same version, in one installer. A release is built once and promoted, so the installer that ships is the one that was tested. Both happen in GitHub Actions on GitHub-hosted runners, which are free for this public repository, following T3 Code's release workflow. Boat is for development, never a fallback. The steps are commands of `tools/release.py`, which the workflows call.

A candidate is built on a Windows runner (`release-candidate.yml`) only when a release needs one: the release workflow's build job calls it, and a dispatch builds one by hand. Nightly and preview use the release profile, stable the fat-LTO one. Main's CI builds no candidates, because a nightly is never waited on and ships only main's newest green commit, so building every commit threw most builds away and held runners that pull-request CI queued behind. T3 Code's release workflow builds only when a nightly is due too. The candidate workflow compiles both apps with the version and this repository's releases as their feed address, and packages the NSIS installer. It then runs the leak gate on the installer and its UI bundle, and checks the installed layout. The map-drawing smoke needs a game installation, so it runs only on a machine that has one. The installer and a manifest of its commit, version, hash and the apps' updater key are kept for 30 days as an artifact named for the channel and commit, and for stable also the version. Rerunning the candidate workflow for a commit replaces an expired one.

The release workflow (`release.yml`) has three channels:
- **Nightly** is automatic, at most once a UTC day. Each hour it checks whether GitHub took the nightly feed today, and if not, releases the newest commit on main's first-parent line after the feed's commit whose CI is green and whose workflows are main's: CI ran and every check on the commit settled green. Main's tip is usually still in CI, and a push whose run a newer one replaced never turns green, so taking only the tip published nothing; GitHub also drops many scheduled runs, so the check runs hourly rather than once. A push's CI tests only what changed since main's last green commit, so while main's last whole-workspace CI run, the scheduled one, has failed, been cancelled or is still going (a retry shows only its newest attempt), no nightly is due, and publishing checks it again after the candidate's build. A dispatched nightly is not held to the day, and may name its commit. Main's CI is every workflow the push started; scheduled and dispatched runs, the release's own among them, don't count. It does nothing otherwise, while the repository variable `PAUSE_NIGHTLY` is true, or while another nightly release run is going, so at most one nightly builds at a time and a tick during a build queues nothing. A due nightly builds its candidate and then publishes it, unless a kept candidate of that commit exists, such as one a failed publish left, which it promotes without compiling.
- **Stable** is manual, a `workflow_dispatch`. By default it takes the commit the nightly feed offers and the version that nightly previews. Its candidate needs its own fat-LTO build, because the version is compiled in. A dispatch with `prepare` builds it ahead, so the release itself only promotes; without one, the release builds it first. After the release, finalize pushes the version bump straight to main over SSH with the release deploy key, which main's ruleset lets bypass its pull-request rule. Only finalize, in the `release-stable` environment, uses that key. It fetches main again and re-stamps whenever main moved first, as T3 Code's finalize does. A push with a deploy key starts main's CI like any other, but a scheduled nightly is not due for the bump alone: it waits for a commit besides it, so a nightly always ships a change. An older release never sets the version back. Without the key the stable release still publishes, and finalize fails, naming what is missing.
- **Preview** is a test train: built on dispatch, published as a draft with no feed, never offered to installed apps.

Neither public channel installs itself. The apps show an update badge, then the user clicks to download and clicks to install.

Installed names carry the channel: a nightly is BattlePlan (Nightly) and BattlePlan Recorder (Nightly), any other build (Alpha). Tauri's installer keys an install on its product name, so that stays BattlePlan and the channels replace each other in one install, as T3 Code's do. The installer hooks, both apps and their build scripts take the label from `BATTLEPLAN_VERSION` and put it on the Start menu and desktop shortcuts, the installed-apps entry, the window title, the tray and each executable's description; the build scripts hand the labelled name to Tauri's build step alone, so the bundle keeps its product name. The recorder's Start with Windows entry keeps one name across channels.

Choosing the other channel in either app offers that channel's current release even when it is older than the running build, because stable usually trails nightly; the restart prompt names it as an older version and warns that recordings made with the newer build may not open in it. Once a build runs on its chosen channel, only newer releases are offered. The installer allows downgrades for this.

The workspace version in Cargo.toml is the last stable release. A nightly or preview is the next patch with `-<channel>.<yyyymmdd>.<n>`: the UTC date of its build and the commit's position on main's first-parent line. Public channels take only commits on that line, so each position names one commit, and candidates built in main's order sort in that order. A stable candidate is that next patch, or a version named for a larger step. The build passes the version as one variable, `BATTLEPLAN_VERSION`. Only app-update, the recorder and Tauri's bundle read it, so the workspace version in Cargo.toml stays the last stable release, and where the build folder persists a new version recompiles those crates alone. A build without the variable, or with it empty, takes Cargo's version. On a hosted runner each candidate is a cold build: 73 to 92 minutes on 4 vCPUs, nearly all of it the workspace's crates, with only downloaded crates cached. Compiler caching gave no speed-up that could be measured, so none is used. The leak gate then takes under half a minute. Publishing compiles nothing, so a release takes minutes once its candidate exists; a nightly takes its build's time plus those minutes. The version and the feed address are compiled into both apps, which compare the version with the feed's and record it in recordings, and the installer carries the version in its own metadata. Changing the version after the build means compiling again, and reading it at run time would let one binary claim several versions. So publishing never changes it, and a candidate belongs to one channel.

Stable and preview releases run one at a time, queued; nightlies run one at a time by yielding to one already going; dry runs run apart. A candidate is taken only from an artifact this repository's main built: the candidate workflow dispatched on main, or the release workflow's build job. Its manifest must name the commit and version the release resolved. A commit whose workflows differ from main's is refused before building or signing, because GitHub refuses the workflow's token a release of it. Publishing takes the candidate and, in order:
1. It runs a preflight that fails with a named reason for each of these: the updater key is missing, is not one line of Tauri's base64 minisign secret key, has the wrong password, or is not the key the apps carry; some Azure settings are set but not all; no private terms are set; the repository is private and the channel is public.
2. It checks the installer's hash against its manifest.
3. It refuses:
   - a commit not on main's first-parent line, or one that does not contain the feed's commit;
   - a version not newer than the feed's or the channel's newest release;
   - a tag already on another commit.
4. It signs the installer with Authenticode when the Azure settings are set, then with the updater key, bound to its version. It verifies both and checks the signed installer's layout again.
5. It writes notes from the titles of pull requests merged since the channel's previous release.
6. It publishes the installer and its signature, then the feed, which it reads again just before replacing it. A client that sees a new feed can therefore download its target.
7. It checks the published assets against their hashes, and that the feed offers the channel's newest release.

Authenticode signs only the installer, because signing the binaries inside it would mean packaging again at release time. The certificate data it appends goes through the leak gate.

Each channel's feed is `latest.json` on a release named after the channel, kept a prerelease and never the latest, because the apps read `<releases>/download/<channel>/latest.json`. Each release's text records its source commit and the signed installer's hash. A rerun after the feed was published only checks it, so finalize still runs. A release whose feed upload failed is taken up again on a rerun, from its published installer, only while it is the channel's newest release and only if that installer is the one its text records. A dry run, `draft`, publishes everything to a new draft release and leaves the channel's feed alone.

The updater key and the Azure signing settings are secrets of the `release` environment, and of `release-stable`, which requires a reviewer. `release-stable` also holds `RELEASE_DEPLOY_KEY`, the private half of the deploy key that writes the version bump. `LEAK_GATE_TERMS` is a repository secret. Release assets have no storage quota.

Both apps carry the Tauri updater verification key. It was replaced before any release shipped, when the earlier private key proved unrecoverable. Tauri decodes the key file as stored, so Git preserves its bytes and the file has no trailing newline. The installer smoke opens the app from an extracted install layout and reads a copied recording without installing software or writing user data.

Candidate builds map the runner's home, Cargo, rustup, checkout and target paths to neutral roots, so the binaries name nothing of the machine that built them. The leak gate checks the installer and the files inside it, the UI bundle, and the release notes and publication metadata. Installer asset names omit spaces, so their published names match feed URLs. The machine-path check allows specific checkout paths in the scripts that configure this machine. The leak gate allows authors' contact addresses in shipped licence notices. Private terms and signing-key material have no path exemptions.
