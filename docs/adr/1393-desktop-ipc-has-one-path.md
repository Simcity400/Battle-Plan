# 1393. Desktop IPC has one path: the IPC custom protocol

The UI reaches the desktop host only through Tauri's IPC custom protocol (`http://ipc.localhost`). The desktop app and the recorder replace Tauri's invoke script with this one (`Builder::invoke_system`). That script has no postMessage fallback.

Tauri's own script falls back for good once any custom-protocol fetch rejects, and then sends every call over `window.ipc.postMessage`. That path is far slower: replies come back as evaluated script. A reload, including the e2e sweep's `Page.reload` and the user pressing F5, cancels the page's in-flight IPC fetches. The unloading page then took that as the protocol being blocked and re-sent each call over postMessage. The commands ran twice, and its `listen` calls registered event listeners for a page that no longer existed.

- A request that fails while the page is live rejects that invoke with a named error ("BattlePlan couldn’t reach its desktop host for <command>: …") and logs it. The next invoke still uses the custom protocol. Dashboard queries show that sentence (`queryFailure` takes the string rejection as a shown error).
- A request lost after a `pagehide` that unloads the page is dropped. The page that asked is gone, and the new page makes its own requests. A page kept in the back/forward cache (`persisted`) still hears its failures, so no invoke is left waiting.
- A plain array payload is sent as those bytes (`Uint8Array.from`).
- Nothing is retried on another path. Each failure below is shown by name with its own Try again, which repeats only that failure's step.

## Closing asks the live page

A failed reply can come from a request the host still applied, so any copy of the page's unsaved state kept in the host can fall out of order with the page. The host keeps no copy. The live page is the only judge of unsaved work, and it judges when it is asked. The host (`leaving.rs`) owns which questions stand and which leaves it has accepted; the page (`closeGuard.ts`) owns every judgment of unsaved work.

**Host.** The main webview's page is *loading* (no subscription yet; BattlePlan starts here), *watched* (one subscription), or *gone* (its process exited). Beside that the host keeps the pending navigations as a set of WebView2 navigation ids (WebView2 gives them no order), the questions it waits on, and its *holds*: the leaves it accepted.

- A question is a `close` (the window's close button), an `install` (BattlePlan's own update at its last step), a `leave` (the installer's close request on the control pipe) or a `query` (the other app's busy query). It gets a fresh id when it is asked, and again for each new subscription. The host *waits on* an id until it is answered or retired, and *holds* a leave it accepted.
- A leave answer to a `close`, `install` or `leave` becomes a hold, kept until BattlePlan exits; only an install whose installer couldn't start is released (`stay`). Setup's close commits the exit when the host takes it. The host waits for the page's answer to setup's close for 10 seconds and to a busy query for 2, then gives the question up under its lock and answers setup by name; the page's late answer comes back `false`.
- *Loading*: update questions are refused by name, and a window close waits; a second close opens the native choice. A subscription from this document (`close_watch_document`, then `watch_close_requests` with a sequence number and a callback) makes the page *watched*. A subscription from another document is refused, and only a newer sequence replaces one, so a lost reply sent again changes nothing.
- *Watched*: each new or replacing subscription is sent every waiting question again, with fresh ids, and the holds.
- A navigation (`NavigationStarting`) is refused while any hold stands, so F5 can't bring back an editable page while BattlePlan leaves. An allowed one retires every waiting id at once: update questions are refused by name and closes wait. While a navigation is pending the host sends the page nothing: WebView2 runs a script executed after `NavigationStarting` in the incoming document as it loads (`ExecuteScript`), so the page the reload is leaving would never hear it. Leaving while a navigation is pending stops it (`Stop`), so that page stays and hears the holds once the navigation completes. A new document (`ContentLoading`) makes the page *loading*; if a hold stands, which happens only to a reload whose document began loading before the stop took hold, the host stops that document too. A navigation that ends without one (`NavigationCompleted`, a stopped or failed reload) keeps the subscription, and the page is sent what stands then, even when nothing does, so a page locked for a question the reload retired hears that it is gone; the waiting closes are asked again.
- Every way BattlePlan leaves commits through one transition (`State::exit_as`), under the lock that decides it: an accepted close, "Discard and close", the native choice, setup's close, a started installer, a page gone with a close waiting, Windows ending the session, and any exit Tauri asks for. It seals the exit (below), refuses by name every install still asked or judged, answers setup's leave and busy queries, retires the waiting closes, and disables and hides the main window, so a dialog it owns can't show it again. An install the host accepted earlier keeps its receipt and is waited for.
- If any of these WebView2 handlers can't be registered, the host claims nothing it can't see: a subscription is refused with the reason, which the page shows, update questions are refused by name, and every close opens the native choice, saying why. This comes before every other state: a crash it does see closes nothing, since a reload it can't see may have brought back an editable page.
- *Gone*: the page held nothing that can be saved, so a waiting close closes BattlePlan, committing first, so an install still waiting is refused by name; the update questions left are agreed to, with holds. Holds outlive the process, so a crashed page can't be reloaded while its installer starts. A close goes through. The page's process takes its pending navigations with it, so setup is never told a dead page reloaded.
- A page that stops answering input (`RenderProcessUnresponsive`) refuses waiting update questions by name, and it or a second unanswered close opens one native choice: keep waiting, or close and lose anything unsaved. Keeping waiting lasts the hang: WebView2 repeats the report while the page stays hung, and no repeat offers the choice again until the page runs a batch, answers, subscribes, reloads or ends, or the user closes again. No timer decides for the page.

**Messages.** The host sends to the page's callback as script, not on a Tauri channel: a channel numbers each message before it is sent and the page holds every later one until a missing number arrives, so one failed send would leave a live page deaf. Each script is one batch: a sequence number, every question waiting (its id and kind) and the holds. Every batch says all that stands, so the page applies only a batch newer than the last it applied; an older one is covered by it. Batches may therefore run in any order, as they do: Tauri runs a script dispatched from the UI thread at once and queues one dispatched from another thread. The host collects batches under its lock and dispatches them after releasing it, so a dispatch refused at once, whose dropped callback reports straight back, can't deadlock. A batch is delivered only when the page's callback returns `true` (`eval_with_callback`); a dispatch refused, a WebView2 execution error, a webview gone, a callback dropped without a result, and a guard that has ended all count as undelivered. A question is undelivered only when every batch that carried it was. An undelivered update question is refused by name, which wakes setup; an undelivered close opens the native choice, and the next close asks again. An undelivered batch never means the page is gone.

**Page.** The guard is *editable*, or *leaving* while it holds a commitment or the user chose "Discard and close". Leaving locks editing ("Closing BattlePlan…" or "Restarting…" in a modal, rendered with `flushSync`) before any answer is sent.

- On each newer batch the guard first drops every commitment the batch doesn't list as waiting or held, and its failures with them, then takes the holds as its own, accepted commitments, then judges each waiting question it hasn't judged from its state at that moment: its layouts from the dashboard's latest drafts and its theme from its latest edit, never a rendered copy. A commitment is accepted once a batch holds it or the host replies `true` to its answer.
- A batch counts as handled only once the guard has judged every question in it. If reading the page's state throws, the callback returns `false` and the failure is shown by name with Try again. An older batch judges only the questions it carries that the newest batch still lists; a question it doesn't carry waits for a newer batch. The guard keeps the newer batch's holds and retirements, so an older one can't undo them.
- Unsaved work keeps a `close` and shows the prompt, keeps an `install` unless the user chose "Discard and restart" for it, keeps a setup's `leave`, and makes a `query` busy. The page answers from one registry of pending work (`pendingWrites.ts`). Every write the page sends goes through one client wrapper (`writes.ts`) that enters it when sent and leaves on reply; a form that keeps an edit the host refused, or a folder typed but not applied, holds it there too, in the registry rather than the field so it survives leaving the page, until it saves or is discarded, and a change still queued in the page counts from when it was made. The prompt says a settings change is still being saved, or isn't saved. The leave the user asked for stands until it succeeds or is cancelled: **Save…** sends each failed change again through its own retry, or opens the editor or settings that hold the rest, keeping the request through them, and once nothing is unsaved the close or restart goes ahead. A theme edit counts from the moment the editor takes it. A leaving guard agrees to every close, install and leave. A query never changes the page.
- A leave answer with unsaved work names the commitments it rests on (its basis), all of them accepted. While any commitment is still unaccepted, a question that would rest on it waits, unjudged, until the commitment is accepted, refused or retired; a lost answer shows its Try again meanwhile. The host takes a leave only if every id in its basis is a hold, never an answer it merely waits on; otherwise it asks again with a fresh id. So no answer resting on a commitment the host never took or has retired can close BattlePlan, however its batch and the retirement cross.
- An answer the host no longer waits on comes back `false`, and the guard drops that commitment.
- Try again never acts on what the page last heard, which the host may have retired since (a close whose only batch couldn't be judged is retired by that batch's receipt, and turned into the native choice). It asks the host for a fresh batch (`refresh_close_requests`, honoured only for the subscription that asks), which replies with that batch's sequence number, and judges or answers against that. The host refuses by name while a navigation is pending, since it sends the page nothing then, so a request never reports a batch it didn't dispatch. A failed judgment is judged afresh from it, with the fresh ids the host gives what it asks again. A failed answer is sent again only from a batch at least as new as the one its request brought, which a batch queued before the request can't be, and only if that batch still lists its id as waiting, and then as the same answer, never a new judgment, which could rest on its own lock. An answer's failure goes with the first batch that doesn't list its id as waiting: the host has either taken it, and holds it, or retired it. A request for a batch that fails keeps the failure, with its Try again. Each failure has one request out at a time: Try again while it is out does nothing, and its reply acts only while its failure is still the one shown, so a reply for a failure since replaced, by an answer sent again whose reply was lost, sends nothing.
- An install that couldn't start, or whose reply was lost, asks the host for a fresh batch, so a stay whose batch was lost never leaves "Restarting…" up. Every batch says whether an install the page asked for is still on its way (`installing`): the page numbers each install request with its document, the host opens that attempt when the request is dispatched and ends it when the command returns, and Try again's request for a fresh batch names the newest attempt, so the host gives up any it never saw. The page keeps that install unresolved, and if the question then locks it for the update, the lock shows Try again. The install is resolved once the page applies a batch at least as new as one the host named with no update standing and no install on its way, or the update lock ends. A request that fails says so there.
- "Discard and restart" is the confirmation for the install it starts; Cancel withdraws it, and once the page has answered the dialog can't be cancelled. "Discard and close" locks editing, then leaves (`leave_app`). app-update starts one install at a time.
- A guard that ends (React Strict Mode) handles nothing more, and its callback returns `false`. Its replacement subscribes with a newer sequence number. The app makes one guard per document (its effect depends only on a stable callback), and Strict Mode's replay ends the first as it mounts, before its first subscription can resolve, so no guard is replaced after it could have locked the page. Fast Refresh in development can remount one later; that is outside what this design guarantees.
- Each failure is shown by name with its own Try again: the subscription, a failed close, and each answer. In the modal they show inside it.

The control pipe still answers a close request with one byte. After a refusal it sends the refusal's own words, which setup shows ([ADR 0006](0006-installer-coordination.md)).

The randomized test in `leaving.rs` drives the host against a model of this guard: questions, answers and their loss, batches run in any order, dropped or refused, reloads, crashes, unresponsiveness, installs that start or fail, Try again and its replies, and what still happens once BattlePlan leaves. It checks that unsaved edits are lost only by the user's choice, no page loads or is editable while a leave stands, every question is answered, refused by name or turned into the choice, no page stays locked with nothing standing and no Try again, and no install is accepted once BattlePlan commits to exit. For each seed that adds a kind of guard event not seen yet, it keeps what the model guard was given and did in `ui/src/shell/closeGuard.traces.json`, and fails if that file differs (`BATTLEPLAN_WRITE_TRACES=1` rewrites it). `closeGuard.test.ts` replays those traces through the real guard and requires the same answers, locks, prompts and failures.

## The recorder panel's prompts

- The recorder keeps each tray Quit or Discard prompt with an id and the key of the session it asks about, and publishes the pending one in its status. A panel, new or reloaded, shows what the status holds. Cancel retires prompts by id in the recorder, with only the Quit intent those prompts carry. A Discard asked about one session is dropped when another begins; a pending Quit asks again about the new one, with a fresh id.
- Every status carries the recorder's revision, counted under its lock. A status is sent after the lock is released, so an older one can arrive after a newer one; the panel shows only a newer revision. A compact panel closes itself with the revision it judged, and the recorder refuses if the prompt changed after it. A prompt counts as seen only when the user acts on it: the panel reports a click or key inside the prompt (`prompt_seen`). The window's state can't prove what the user saw (a visible window may be covered, off screen or only queued to show), so nothing drawn or shown counts. Closing the panel cancels only prompts the user acted on; a lost report counts as unseen. A click away, the tray icon or Cancel on the message that the panel couldn't be shown dismisses the panel: no panel opens by itself, and a prompt left waits, named in the tray's tooltip, until the user opens the panel. A long recording name is cut before the question is. After a panel closes itself, a prompt left opens the panel again. A panel closing itself cancels nothing asked after the status it judged, even if it showed it before the window went.
- Save and Discard name the session the user saw (`stop_recording` with its key), and Discard names that session's campaign. The panel's own Stop and its Discard step are kept with the key of the session they were opened for, and shown and sent only while the status is about that session, so a status about another session never inherits them. A Save or Discard, and its Try again, acts only while the screen still offers it for that session: cancelling the Discard step back to Save or Discard retires that Discard's Try again. The recorder takes a stop only for its live session, and the same request sent again changes nothing. The capture seals its ending once, when the journal has closed and before it settles what it keeps, and refuses any stop after that, so a session that is already saving can't be turned into a discard. A discard then drops only the campaign the user confirmed, and only if the game names it as the one in progress when the capture takes up the stop. If that read fails, or there is none, nothing is discarded, even when the recorder saw that campaign earlier, and the recorder says why. A Save names the campaign the user confirmed too, and the capture keeps that one, even if the game has loaded another since. Each campaign has one accepted decision, the latest by when it was accepted; a batch acts on the latest choice for each campaign, and a decision retried while history is held goes back ahead of later ones and never over a newer one for its campaign. Decisions the capture hadn't taken up when its session ended are settled once, under the finalize lock and before anything else can end the session: one for an earlier session's campaign in the same folder is saved or discarded there, keeping a saved path for compression; one for this session's sets its destination, a Discard first cancels any Save the game was still holding, and is then rolled back to the last saved revision with its waiting row removed, so Auto save never publishes it. A waiting row's action goes to the capture that owns its folder; once that capture has taken its decisions, the action waits for the folder's lock, reads the row again under it, and settles on disk. A capture whose collector never detaches names each decision it couldn't carry out in its error. Panel settings commands take their receipt when they arrive, before any lock, so a Quit can't seal past them; the panel sends each change at once, reads what is stored once overlapping changes are answered, and shows each change's warning. Dismissing the panel while its requests are out hides it, and it closes when they are answered; the tray opens a hidden panel again rather than closing it twice.
- A prompt stays until the recorder answers; a failure is shown in the prompt with Try again and keeps a compact panel open. A failure whose prompt the status already retired is shown on its own, so the panel it keeps open is never blank. A panel that can't size or close itself says so with Try again; one that can't be sized is still shown, so that line is seen, even while it is still connecting. A panel is shown as soon as its window is built, at its opening size, whatever its page does; opening it again while its window is still hidden shows it. The main thread owns the panel's size: the opening placement and the page's fit both run there, and the opening size applies only until the page has fitted, so the page's size wins whichever runs first. A panel that can't be shown says so in a native message with Retry and Cancel; Cancel closes it, keeps its prompt for the next time the tray opens the panel, and opens no panel by itself. The answer acts only on the window it was asked about: if that panel has closed since, it does nothing, even to a panel opened in its place. Each panel window is its own instance, retired when it is destroyed; its events, its page's commands and its messages change the shared panel state only while it is the live one, and its page's own close and its reports of prompts acted on are kept with it, so a panel opened in its place inherits nothing from it.
 Failure lines stand above a Stop prompt, never in the region it covers.
- The command-line recorder keeps Ctrl+C as a quit for the whole process, apart from each capture's stop. Ctrl+C while recording saves the capture, and Ctrl+C during finalization or between games ends the recorder once the capture is done.
- The panel reads its opening state (`panel_opened`) once; a failed read is shown with Try again. A read that comes before the panel's window is registered as the live one fails as still opening, so an opening that succeeds has registered its panel.
- Escape does nothing to a prompt whose Save, Discard or Cancel is on its way.
- The recorder commits through one transition too (`Inner::exit`): tray Quit, a Quit prompt answered with Save or Discard, a Quit left waiting when its session ends, setup's close, a started installer, Windows ending the session and any exit Tauri asks for. It seals the exit, refuses a pending install by name, starts no capture and asks a capture under way to save. Setup's install takes its receipt in the locked step that decides it, so a Quit either refuses it or waits for its launch. A capture takes its receipt before it touches the save folder, so a refused one consumes no New file. The tray says it is saving and then quitting.
- The tray's icon, tooltip and menu are applied on the UI thread from the newest status by revision, so a status worked out before a Quit question but sent after it can't erase it.

The script runs in every webview either app opens, in development and in the packaged app alike. It is adapted from Tauri's IPC protocol script, and Tauri's licence ships in the third-party notices.

## Leaving

**One exit.** Each process has one exit coordinator (`replay_settings::exit`). Work that must finish before the process ends takes a receipt from it and keeps it for the whole operation, its compensating writes included: a settings or preference file, a recording rename, a map export, an installer launch, a capture, a waiting recording's save or discard, an abandoned session's recovery. A thread can carry its receipt, so what it nests and the threads it starts continue after the exit commits. A file lock is taken before admission, so a save waiting on another instance holds nothing the exit waits for. An installer launch and other work exclude each other, refused by name. Each file is written beside its destination and replaces it only once whole; a name with no folder is written in the current one. Committing seals the coordinator: nothing new is admitted, and each refusal says BattlePlan is closing.

**The exit thread.** Each app starts one exit thread before Tauri. It waits for the seal, then for every receipt; once that takes more than a moment it shows one window, which can't be closed, naming what it waits for and anything stopped. It then stops the control pipe, marks the exit done, runs the bounded cleanup (in the desktop the page's last measurements, then the maps, the dashboard's workers and the measurement summary within five seconds), asks Tauri to exit, and ends the process five seconds later if Tauri hasn't. Tauri's `ExitRequested` is refused until the exit is done. No window-owning thread waits on another thread's window: the Saving window is told what to show without waiting, a pop-out's focus is posted to its map, and panels, pickers and native choices are shown outside the coordinator's and the host's locks.

**Windows ending the session.** Windows sends every top-level window `WM_QUERYENDSESSION`, then `WM_ENDSESSION`; with `wParam` TRUE the session may end as soon as every window has returned ([WM_QUERYENDSESSION](https://learn.microsoft.com/windows/win32/shutdown/wm-queryendsession), [WM_ENDSESSION](https://learn.microsoft.com/windows/win32/shutdown/wm-endsession)). Tauri turns `WM_ENDSESSION` into `RunEvent::Exit` with no `ExitRequested`, so each app follows the session itself (`app_update::session`): the desktop subclasses its main window, and the recorder makes a hidden top-level window. On `WM_QUERYENDSESSION` it returns TRUE and commits nothing, since the end can still be cancelled. While receipts are held or a recording is live it names that with `ShutdownBlockReasonCreate` ([Shutdown changes for Windows Vista](https://learn.microsoft.com/windows/win32/shutdown/shutdown-changes-for-windows-vista)); the desktop also asks its page whether drafts are unsaved, and takes the answer only if it belongs to the newest query. On `WM_ENDSESSION` TRUE, and on `RunEvent::Exit`, it commits and waits on the UI thread for the exit to be done, serving messages other threads send it meanwhile and refusing to wait again inside one. `ShutdownBlockReasonDestroy` releases the reason, also when the end is cancelled.

**The control pipe.** Stopping the pipe server closes admission and wakes an idle connect or read at once. A request already accepted keeps the pipe through its decision, its reply (two seconds) and setup closing its end (five seconds), so setup reads the `Y` it was promised. A broken pipe after the decision is logged as an unknown delivery outcome.

**Exports.** A map export isn't a message on the map's wire protocol: the host admits it and hands the map a job that owns its reply and its receipt. A job the map never runs answers that BattlePlan stopped it when it is dropped, so the exit never waits on a map that went away.

**Consequences.**

- Unsaved dashboard drafts are lost when Windows ends the session. The page is asked only so Windows can name them while it waits.
- If Windows ends the recorder before a capture finishes saving, the spool is recovered on the next start ([ADR 0802](0802-recorder-admission-and-recovery.md)).
- If setup's read of `Y` still fails, setup goes on without the restart it would otherwise run ([ADR 0006](0006-installer-coordination.md)).
- Compression isn't waited for: the seal cancels queued compressions and stops the running one, and the Saving window names each, staying up for four seconds on an ordinary Quit so they can be read, but not while Windows waits on the session end; the recording stays usable.
- A file whose flush Windows didn't confirm is already visible, so the write boundary returns it as applied, with a warning (`replay_settings::exit::Applied`), never as an error. Every caller finishes its change on both (recorder settings and **New file** among them), and every screen that shows a save shows the warning without offering to make the change again. A settings change that set Start with Windows keeps the new value. One that failed outright puts back the value Windows held, with its type and bytes.

## Locks

No lock in either app is held across a call that waits on the UI thread: a window's getters (its handle among them), the tray's calls, `run_on_main_thread` waited on, a cross-thread `ShowWindow`, or a dialog. The UI thread takes these locks while it handles focus, tray clicks and window events. Read what the UI thread owns first, then take the lock; read a handle under the lock and call the window after.

No lock a window or tray handler takes is held across a filesystem read or a file lock either: the recorder's recording caches have their own lock, the recordings list reads its files before it takes the panels' names, and the desktop's video settings are held only to read or apply them, with the file saved between, by commands that run off the UI thread. A diagnostics or mute change is decided from the saved file under its file lock, and one serialization covers deciding, saving and announcing it (with `--diagnostics` consumed under the file lock), so two toggles never collapse into one and the newest announcement is what was saved last. The recorder reads a finished recording's size, hour span and campaign before it takes its lock.
