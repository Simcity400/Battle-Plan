# 1393. Desktop IPC has one path: the IPC custom protocol

The UI reaches the desktop host only through Tauri's IPC custom protocol (`http://ipc.localhost`). The desktop app and the recorder replace Tauri's invoke script with this one (`Builder::invoke_system`). That script has no postMessage fallback.

Tauri's own script falls back for good once any custom-protocol fetch rejects, and then sends every call over `window.ipc.postMessage`. That path is far slower: replies come back as evaluated script. A reload, including the e2e sweep's `Page.reload` and the user pressing F5, cancels the page's in-flight IPC fetches. The unloading page then took that as the protocol being blocked and re-sent each call over postMessage. The commands ran twice, and its `listen` calls registered event listeners for a page that no longer existed.

- A request that fails while the page is live rejects that invoke with a named error ("BattlePlan couldn’t reach its desktop host for <command>: …") and logs it. The next invoke still uses the custom protocol. Dashboard queries show that sentence (`queryFailure` takes the string rejection as a shown error).
- A request lost after a `pagehide` that unloads the page is dropped. The page that asked is gone, and the new page makes its own requests. A page kept in the back/forward cache (`persisted`) still hears its failures, so no invoke is left waiting.
- A plain array payload is sent as those bytes (`Uint8Array.from`).
- Nothing is retried on another path. Each failure below is shown by name with its own Try again, which repeats only that failure's step.

## Closing asks the live page

A failed reply can come from a request the host still applied, so any copy of the page's unsaved state kept in the host can be out of order with the page. The host keeps none. The live page is the only judge of unsaved work, and it judges at the moment it is asked.

- Each document the main webview loads gets a number from the host, counted at each page start (`close_watch_document`). The page subscribes with that number, a sequence number and a callback it registered (`watch_close_requests`). The host refuses a subscription from any other document, so one the outgoing page sent before a reload can't take the new page's place. Within a document, only a newer sequence replaces the subscription, so the same one sent again after a lost reply, or an older one arriving late, changes nothing. A superseded subscription in the page is inert.
- The host sends to that callback as script, not on a Tauri channel. A Tauri channel numbers a message before it is sent, and the page holds every later message until the missing number arrives, so one failed send would leave a live page deaf.
- Each script is one ordered batch: every `stay` the page hasn't confirmed, then the questions. The page takes them in order, and the script returns `true` only once the callback has run them. A batch is delivered only when WebView2 reports that result (`eval_with_callback`). A script refused before it runs, one WebView2 fails to execute, and one whose webview is gone all count as undelivered; Tauri only logs those, so the host counts a callback dropped without that result as one.
- An undelivered batch means the page didn't hear it, never that the page is gone; only a page process that exited is gone. An undelivered update question is refused by name, which wakes setup. An undelivered close opens the native choice, including a close held while the page started and sent when it subscribed, and the next close asks again. An undelivered `stay` goes with the next batch, before its questions.
- The host asks with a fresh id each time it sends a question, and the page answers from its state at that moment (`answer_close_question`). A question still waiting when a newer subscription arrives is sent to it with a new id, so the superseded page's late answer settles nothing. The page reads its layouts from the dashboard's latest drafts and its theme from its latest edit, not from the copy the dashboard reports after it renders.
- A question is about a `close` (the window's close button), a `leave` (the installer's close request on the control pipe, and an install at its last step) or a `query` (the other app's busy query). Unsaved work keeps the window and shows the prompt, or refuses the update with the update message. A busy query never changes the page.
- Agreeing to leave locks editing first: the page shows that BattlePlan is closing until it exits or the host sends `stay` for that question (an installer that couldn't start). The host keeps every leave it accepted until it exits or sends that `stay`, so the same answer sent again after a lost reply is still accepted and the page stays locked. An answer for an id the host superseded, or one after its `stay`, lets the page go on, and a `stay` clears the failed answer it settles. With a `stay`, the host asks again, with fresh ids, every question it had sent and not had answered, so no answer the page gave while still leaving can close BattlePlan after the page went on.
- While the host holds an accepted leave, the main webview refuses to navigate, so F5 can't bring back an unlocked page while the installer starts. A navigation it allows starts a new document at once (WebView2's `NavigationStarting`), before the new page loads: the outgoing page's questions are refused by name, and its later answers commit nothing.
- "Discard and restart" is the page's own confirmation, given as its answer when the install asks at its last step. Cancel withdraws it before editing resumes, so a question asked after Cancel is refused; once the page has answered, the dialog can't be cancelled. "Discard and close" locks editing, then leaves (`leave_app`).
- Before a page starts there is nothing to keep, and a close goes through. A starting page (wry's `Started`, at WebView2's `ContentLoading`) is a new document: questions the old one left unanswered are refused by name, update questions are refused by name until the new page subscribes, and a window close waits for the subscription. A page whose process exits (WebView2's `ProcessFailed`, browser or render process exited) held nothing that can be saved, so its questions are released and closes go through.
- No timer decides for the page. WebView2 reports a page that stops answering input (`RenderProcessUnresponsive`), and each report refuses the update questions waiting on it by name. Such a report, or a second close while the page hasn't answered the first, opens one native choice: keep waiting, or close BattlePlan and lose anything unsaved.
- The control pipe still answers a close request with one byte, and after a refusal it sends the refusal's own words, which setup shows ([ADR 0006](0006-installer-coordination.md)).

## The recorder panel's prompts

- The recorder keeps each tray Quit or Discard prompt with an id and the key of the session it asks about, and publishes the pending one in its status. A panel, new or reloaded, shows what the status holds. Cancel retires prompts by id in the recorder, with only the Quit intent those prompts carry. A Discard asked about one session is dropped when another begins; a pending Quit asks again about the new one, with a fresh id.
- Every status carries the recorder's revision, counted under its lock. A status is sent after the lock is released, so an older one can arrive after a newer one; the panel shows only a newer revision. A compact panel closes itself with the revision it judged, and the recorder refuses if the prompt changed after it. The panel tells the recorder which prompt it showed (`prompt_shown`), from the prompt once it is on screen, so a panel on another view reports nothing until it shows the prompt. Closing the panel cancels only prompts it showed, and a prompt it never showed opens the panel again; a lost report counts as never shown, so its prompt comes back. A panel closing itself cancels nothing asked after the status it judged, even if it showed it before the window went.
- Save and Discard name the session the user saw (`stop_recording` with its key), and Discard names that session's campaign. The recorder takes a stop only for its live session, and the same request sent again changes nothing. The capture seals its ending once, when the journal has closed and before it settles what it keeps, and refuses any stop after that, so a session that is already saving can't be turned into a discard. A discard then drops only the campaign the user confirmed, and only if the game names it as the one in progress when the capture takes up the stop. If that read fails, or there is none, nothing is discarded, even when the recorder saw that campaign earlier, and the recorder says why. A save may still keep the campaign last seen.
- A prompt stays until the recorder answers; a failure is shown in the prompt with Try again and keeps a compact panel open. A failure whose prompt the status already retired is shown on its own, so the panel it keeps open is never blank.
- The command-line recorder keeps Ctrl+C as a quit for the whole process, apart from each capture's stop. Ctrl+C while recording saves the capture, and Ctrl+C during finalization or between games ends the recorder once the capture is done.
- The panel reads its opening state (`panel_opened`) once; a failed read is shown with Try again.

The script runs in every webview either app opens, in development and in the packaged app alike. It is adapted from Tauri's IPC protocol script, and Tauri's licence ships in the third-party notices.
