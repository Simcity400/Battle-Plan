# 1109-E. Retain map icon windows across owners and frames

The map constructs and registers each pool's windows up front. Its initial capacity is selected by icon type. An owner retains its slot across frames, and a new owner takes the next free slot in round-robin order. The manager erases empty icons before their transform and erases icons outside the viewport. It compacts the live prefix while visiting the original traversal extent. Admitted windows keep their top-left position and are shown when needed. The drawing list follows visible live windows, so an erased window and its items leave the drawing list even if its fade continues.

Pool exhaustion starts growth and leaves the ungranted owner to retry. The recording cannot establish the game worker's completion frame. The viewer uses the first possible completion frame and counts it in `PoolGrowth` diagnostics. It grows by at least the native step and batches all the outstanding requests so a newly presented view with many eligible icons need not repaint once per growth step. New slots go through the same construction and initialization as existing slots. Free slots can still run transitions and finish hiding held items. When other instances are affected by those hides, callers coordinate the same clock, transition and draw phases across them.

A refused update leaves part of the window unknown. The window keeps its pool slot, position and membership, but draws nothing until its unknown state is repaired. A complete update recovers the fields it writes every time. Parts written only under a specific condition recover when that write or its observed transition happens. A structurally invalid call withholds the window until it is rebuilt. Refusals stay with the slot across owners because the next owner inherits the same window state.
