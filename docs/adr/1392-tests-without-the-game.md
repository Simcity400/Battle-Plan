# 1392. Tests run on a synthetic game, never the installed one

No test reads the installed game. Tests run on a hosted Windows runner that has no game. They get the game's formats from a synthetic game: made-up content files, localisation and executable tables, authored by us. A synthetic table never copies rows, ids or masks from the real one. It names only what our code or test inputs already name, so it is a model of our readers' expectations, not an excerpt.

Each test's fate follows one rule. A test that checks our logic is rewritten on synthetic data. A test whose only work was to confirm facts about the real build is deleted. That covers table counts, digests and the ids of named triggers, plus every read sweeping the installed files or the Workshop. The real build is checked at run time instead: each build-specific part verifies itself and is withheld by name, and `executable-tables-check <game folder>` reports every part (`--pin` regenerates the pinned registry identities).

The fixture has three layers.

- `synthetic-game` is a dev-only crate. `Executable` builds executable tables declaratively. Keywords, triggers and effects are declared by name with ids assigned automatically, or at the id our code names. Auxiliary tables, variables, numeric properties, commands and folding can be declared too, and any part can be withheld. `pinned()` marks the keyword table as holding the fixed ids our code names. `build()` assembles them and `enter()` scopes them to the calling thread, as a recording's tables are scoped in production. `synthetic_game::enter()` alone enters empty tables for tests that only need tables to exist. `Installation` writes a game folder, DLC, localisation, a user folder and a mod stack under the temp folder and removes them on drop.
- engine-executable exposes `executable_tables::synthetic` (constructors for assembled tables) under its `test-support` feature, which `synthetic-game` enables. A shipped build never compiles it. Its own tests locate tables in synthetic PE images from one shared builder (`executable_tables::synthetic_image`), because a crate's unit tests cannot depend on a crate built on it. Anchors the decoders find by hashed game text are not reproduced. Tests drive the locating steps below them on synthetic images.
- A crate whose readers dispatch on identities named in its own code declares the vocabulary bound to those identities beside that code. `content-reader-script` does this in `test_game` (enabled by `test-support`, so dependent crates reuse it). The effect, trigger, keyword, category, stat, rule and strategy rows bind test vocabulary to the reader addresses, token ids and category bits its code names. Bits a normalisation names are honoured, and all others are free. A test needing more declares it with `test_game::with`.
