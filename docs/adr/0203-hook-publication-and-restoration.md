# 0203. Keep hook publication and restoration within one suspension owner

The collector prepares its thread census, range lists, diagnostics and page-protection storage before suspending threads. The held interval uses caller-owned storage and avoids heap use, formatting, locking and destruction. A process-wide lock spans each publication from its first page-protection change through the last restore and resume. This prevents publishers from racing on a shared page or suspending one another mid-publication. Restoration scratch stays available after capture stops accepting allocations.

A census handle belongs to this process and pins the thread identity. A reused thread ID can identify a foreign process's thread before it is opened, so the census checks the opened handle's owner. A terminating thread can refuse suspension before its handle signals. A refusal associated with an exiting thread can be left unheld, and other suspension errors fail publication. The controller raises an idle-priority thread after requesting suspension so it can reach synchronization even on a busy machine. It restores the thread's original priority before resuming it. [Windows thread context](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-getthreadcontext)

Synchronizing an initial set does not complete the census. Discovery repeats until it has held the in-process thread creators and no new thread appears. Prepared storage has extra space for that discovery. Exhausted scratch triggers a bounded retry that resolves every existing hold before growing storage. Repeated churn also has a bounded attempt. A guarded function is busy if a thread is inside it or its live stack may hold a return into it. An unreadable stack is treated as busy. For a counted callback, the flight check covers time spent in a native target outside the collector's executable ranges.

A collector hook family publishes as one unit after its sites pass verification. Runtime rounds share one census and suspension across families. A busy site holds all sites in its family. During restoration, unaffected families may restore while the busy family waits. A batch collects at most one pending publication per family, performs them under one suspension and reports each recorded result through the original publication entry points. A later publication of the same family waits for the next restoration batch. Publication neither claims unknown bytes nor rewrites a refused, unowned site on disable. A failed cache flush restores the prior bytes before threads resume. If publication or restoration remains uncertain, the executable owner retains its code and retries without freeing a possible live target.

The suspension owner proves every thread resumed or exited before releasing handles, diagnostics or surrounding storage. A failed OS resume is reported after resolution. Persistent uncertainty retains the owner in the resume-only path even if the outer detach budget expires. The restoration owner explicitly observes each resume before attempting a storage resize. Final quiescence may temporarily exclude the registered collector worker threads. It joins them before checking the full image. Hook patching includes those workers in its census.

`live_stack_holds` uses volatile reads only within a committed, readable stack region. The suspended thread cannot free that stack while the hold is active. In restoration, `Scratch::restore` temporarily rebuilds the hook slice from the disjoint mutable references supplied by its iterator and clears the pointers before returning. `Scratch::record` checks whether hooks are enabled while that call still has exclusive access. When `Scratch::publish_batch` rebuilds the slice, each pointer came from a distinct exclusive reference in the collect pass and no other path accesses the hooks before the report pass.

The installation diagnostics observe production attempts on the attach thread, including failures a caller handles internally. They reuse the caller's existing sentinel read and preserve the first failed rollback. A publication-wide fault reports the affected family or member sites. Timing measurements remain in caller-owned scratch during holds, with slowest-thread priority recorded as it was before any raise. Once all holds resolve, the measurements are merged into status. Serializing the owned snapshot borrows it to avoid unchecked copies on each status write.

The hook implementation relies on ordinary relocation support and checks owned instructions at publication. Full sentinel authentication and ownership of the replaced span are separate checks. A precise span lets adjacent taps share untouched sentinel bytes. Generated bridges preserve the caller's native register, flag, return and unwind state, including unusual stack alignment at interior sites. A continuation that redirects its own return is refused under a hardware shadow stack. Construction finishes fallible work before publishing. Its retained unwind registration and flight storage stay alive until restoration and quiescence are proved. Synthetic test fixtures keep fake handles away from OS cleanup, even after an assertion fails, and isolate process-wide failure injection in a child process. [Windows x64 unwind format](https://learn.microsoft.com/en-us/cpp/build/exception-handling-x64)

`enabled_drop_retains_relay_and_relocation_without_panicking` deliberately leaks the enabled synthetic owner long enough to exercise its still-live entry and relocation. It restores the bytes of its own test stub before releasing it. `refused_publication_or_unregister_retains_registered_executable_storage` likewise tests dropping an invalid owner with synthetic code only. It restores the authored bytes and removes the retained unwind table before freeing either test page.
