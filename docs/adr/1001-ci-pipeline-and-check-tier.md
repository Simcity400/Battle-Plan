# 1001. One pipeline definition, run only on GitHub's hosted runners

Verification is one pipeline, `tools/ci.toml`, run by one entry point, `tools/ci.py`. Each job declares its tier, its toolchain, its inputs as path globs and its command. GitHub's hosted CI, `.github/workflows/ci.yml`, is the only test runner and the only gate. The public repository runs it at no cost on pull requests, on each push to main and nightly on main. Nothing runs tests on a maintainer's machine, and Boat is only the agents' development compiler: it is never used in CI and never stands in when CI fails. The shape follows T3 Code's `ci.yml`: a `changes` job gives each job its gate, the legs with work run in parallel, and one aggregate `check` job gives the verdict. There are two tiers, as `tools/ci.toml` orders them: `check` for pull requests and `main` for main's runs; a later tier runs the jobs of the earlier ones, and a job of a later tier that would run is left to it.

`changes` runs `ci.py changes`. It plans from the files alone: the crate graph comes from the manifests and no toolchain is asked. A job none of whose inputs changed since the base is skipped, never reported as passed. A `files` job scans the changed files that match, or every file, with its `whole` command when it has one, when the change is wide; long lists are split into command lines that fit Windows. A `crates` job selects the changed crates and their direct dependents. A job naming a `manifest` outside the workspace, as the fuzz build does, also takes as inputs the folders of every workspace crate that manifest builds, at any depth, or every crate when it cannot be read, so a listed set never falls behind its dependencies. A job naming a workspace `package`, as the two dashboard builds do, takes the folders of that crate and of every crate its library builds on the same way, so a change to a crate the dashboard never builds does not run them; a package the workspace lacks is refused by name. Both kinds follow optional dependencies whether or not the build enables them, since the plan resolves no features: the set errs wide, 138 crates for the dashboard where at least 127 are built, and never skips a crate the build compiles. The contract job's `warm` command builds the library with `export-types` and leaves the executable to the job, because the cache keeps no executable. The feature pins `tools/check-feature-unification.py` generates under `cfg(all())` are not dependencies: they name crates a member's tests already build through its own dependencies, so a crate's tests that use another crate declare it themselves. The one exception is `test-unify`, which only those pins reach, so a member's build closure and cost still count it. A change is wide for a job when its definition differs from the base's pipeline (a definition includes its toolchain and group), or a file it always depends on changed: its toolchain's files (for Rust the root manifest, lockfile, toolchain, Cargo configuration, vendored crates and `test-unify`), its `shared` scripts, the files in its `widen` list such as the nextest configuration, or the pipeline's own implementation (`tools/ci.py`, `tools/ci.toml`, the workflow). An edit to `tools/ci.toml` that leaves everything outside its jobs (tiers, toolchains, groups, the implementation list) as it was widens only the jobs whose definition it changed, so adding or changing one job does not run every other job across everything. A wide `crates` job takes the workspace. An unreadable crate graph makes a Rust job not run, never skipped, whenever its gate could be needed, and `changes` fails if it cannot plan a job; `check` fails without an explicit gate decision. A pull request compares with the commit GitHub merged it into, the first parent of the merge commit the run checks out, and with the base the event names only when the checkout is not a merge. The event's base can be older than that commit, and comparing with it charged a pull request with everything main took in between: over 231 runs, 67 had an older base and 44 tested Rust their own change never touched, 9 of them without touching a crate. A pull request runs the Rust tests for the changed crates and their direct dependents only, and Clippy for the changed crates alone (`dependents = false`): a dependent's lints cannot change when its own source did not, Clippy fails on warning findings only on lines the change writes (while denied lints fail anywhere in a checked crate), and the tests compile every dependent. A push to main compares with main's last green commit: the newest commit on HEAD's first-parent line before HEAD whose push or nightly run passed, asked of the Actions API one commit at a time once main has any green run, so an old commit's retry finds its own green ancestor however many runs came after, and a history with none goes straight to a whole run. It runs the jobs whose inputs changed since then, and its Rust tests take every crate whose library builds on a changed crate, at any depth, and every crate whose tests use one of those. So a commit whose run was replaced, cancelled or failed is tested by the next push, and each green commit has had all of its changes tested. Testing the whole workspace on every push spent 75 to 95 runner-minutes each and left jobs waiting up to 17 minutes for a runner. With no green commit to compare with, a push runs everything; when the runs cannot be listed, `changes` fails rather than guess, because running everything against the empty tree ratchets against HEAD's parent, which may be a commit that failed. The nightly, a scheduled run of main's tip, runs every job across everything it covers, whatever changed. Main's Rust jobs say how many crates lie beyond a pull request's scope, and a failing test in one of them is marked so. Reading a file outside a crate's folder at build or test time is not tracked, so only the nightly catches a change that breaks such a read, and a nightly release made before it can carry the break; one made after it cannot, because a failed whole-workspace run holds nightly releases until one passes.

The matrix has one leg per group for its ordinary jobs, and a group is a runner's system: repository checks and UI run in one Linux leg, and tool tests, the feature-unification check and browser tests in one Windows leg, side by side, since every leg costs a runner's setup and a place in the queue the pull requests share. Rust runs on Windows, because Cargo resolves features for the host and the workspace's are Windows'. The runner label for each group is fixed in the workflow, never taken from the matrix, so a pull request cannot choose a self-hosted runner. A job with `shards` (Clippy and the Rust tests) gets legs of its own, at most that many, so the two run beside each other. `changes` splits its crates by their measured costs in `tools/ci-weights.json`: each crate's library build, and its test builds and test runs, in core-seconds on a hosted runner. `ci.py weights` writes the table from a cold run's Cargo timings and nextest report; a crate the table lacks takes the median, costs are whole seconds so every runner sums a split alike, and `changes` refuses a table that is not one, so a broken table fails its own pull request. A leg costs its crates' tests and the library builds they need that a restored cache cannot hold, each once: those of the changed crates and every crate whose library builds on them through normal or build dependencies, not dev ones, or of every crate when a Rust toolchain file changed. The costliest crate goes first, each to the leg it adds least to, so a crate joins the leg already building its dependencies. A job takes the fewest legs, up to its `shards`, whose busiest is within four core-minutes of the least busy any count gives, since a leg that saves less is not worth its setup and its place in the runner queue. Each leg runs `ci.py job --group --jobs`, with `--shard AT/COUNT/DIGEST` for a sharded job, and plans again. A planned job that the leg would not run fails the leg, so a gated job never passes by being skipped, and a leg whose own split of a job differs from the one `changes` digested fails too, so no crate falls between legs.

Each Rust leg restores one cache: a sharded job's own, or its group's, which the group's unsharded jobs (the fuzz build and the two dashboard builds) share as they share the leg. It holds the registry and the whole target folder, workspace crates included. `changes` names each leg's cache, and both workflows build the key from that name. Every job on a Rust runner has a `warm` command, and a test fails while one lacks it, because a job without one builds cold on every run: the group's leg did, averaging over eight minutes, while its key was the list of its jobs, which no run ever saved. A workflow of its own, `rust-cache.yml`, writes the caches when a push to main requests its CI run, not when that run ends, so the cache trails main by one build, not by a CI run and a build. The CI run starts it, not the push, so a release, which waits only for the push's own workflows, never waits for it. It runs beside main's CI on three of the account's runners, only for this repository's pushes, and always builds main's newest commit, so an older push never builds an older pipeline. It runs the `warm` command of each job that restores the cache, one after another in the one target folder, skipping the build and the save when neither a crate, a Rust toolchain file, an input of those jobs nor one of their definitions changed since the folder's commit; a newer cache run waits for a running one rather than cancelling it. Only a folder whose every build succeeded names HEAD as the commit it was built from and is saved; a failed one saves nothing, because its folder mixes units rebuilt at HEAD with the commit it named before. A successful build also removes every unit it did not use, found from Cargo's JSON messages, so a unit that comes back later (a feature or profile setting changed and changed back) is built again rather than found fresh against sources it never saw, and it removes the executables, which no leg reuses and which would not fit the cache. Cargo decides freshness by file times, and a checkout makes every file new. So before Cargo runs, `ci.py times` sets every tracked file and folder to one fixed old time, except the paths that differ from the commit the folder was built from and the folders above them, which are now. A file added or removed makes every file of its crate's folder now, because a new file can change how a crate compiles without being in any unit's dep-info. Cargo then rebuilds exactly the crates whose files differ and those above them, and keeps third-party crates, which it keys by version, not time. A folder that names no commit the clone has makes every file new. A build script that watches no file would compare a stored time instead, so `test-unify`'s watches its own source. The C code that build scripts compile is not rebuilt when only the runner image's compiler changes, as with Cargo anywhere. The cache key holds the lockfile, toolchain and Cargo configuration and the commit. A pull request and the cache workflow both fall back to the newest cache of any lockfile: Cargo rebuilds only the units a changed lockfile, toolchain or configuration touches, and the cache workflow's pruning drops the rest, where falling back to nothing rebuilt every crate on each lockfile change. sccache was removed after it showed no speed-up. Third-party actions are pinned to commits, each with a `# vX.Y.Z` comment so Dependabot's grouped github-actions updates can move the pin and its version together. The comment ratchet exempts exactly that comment after a SHA-pinned `uses:` in a workflow.

Clippy runs through `tools/check-clippy.py`, which fails when Cargo exits nonzero on denied lints and fails on warnings only in lines the change writes. Ratchets compare with HEAD's merge base with the base, so a rollback or force-push ratchets only what HEAD adds to their shared history: restored code already passed there. Hosted runners have no game installation. The tests build with Cargo's `ci` profile and run with nextest's `hosted` profile, which writes a JUnit report, and `ci.py` sorts the failures in it. Every test runs without the game, against the `synthetic-game` crate, except the dashboard crates' (`dashboard`, `dashboard-base`, `dashboard-core`, `dashboard-text`), which need the install until the dashboard rework (issue #169). A failure in one of those crates' test binaries is reported as not run there, under a `not-run` rule of `rust-test` that names the crates and cites the issue, never as passed, and only when three things hold. Nextest reports libtest's plain panic exit. The last panic on the test's own thread is, in full, a missing-install message: the game fixture's named `NotFound` cause, or a direct read's bare `expect` (the rule's `panic`). In any other crate the same panic is a failure. And the test reported no error after it. A test that needs the game reports that by panicking, never by returning early as a pass. A timeout, an abort, leaked handles, or any other panic or error fails the job, and the leg prints every such failure with its output and uploads the JUnit report. The override also needs nextest's summary to show every selected test run, so a cancelled run never passes. The profile stops a test after 10 minutes. The desktop acceptance suite (`tools/e2e`) against a recording has no runner in CI.

Superseded pull request runs are cancelled by the workflow's concurrency group. Pushes to main share one group that cancels nothing in progress: the running push finishes, and a later push replaces the one still waiting. A re-run has its own group, so retrying an older push never replaces the tip's, and the nightly has its own, so it and a push never replace each other. A run per push queued runs behind each other. A push compares with the last green commit, so the next run tests everything a replaced one would have, and its ratchets judge every line added since that commit. The Rust cache warms as each push's run is requested, whether or not that run is later replaced: a waiting cache run is replaced by a newer one the same way, and each builds main's newest commit. A release naming an older commit whose run was replaced needs that commit's run retried first. A push compares with the green commit itself, not a merge base, and takes only a green commit its own history holds, so a force-push that drops commits compares with a green commit both histories share. With no green commit, main compares with the empty tree, and its ratchets compare with HEAD's first parent, or are not run without one. The verdict is a failure if any job failed, an error if a job that should have run could not, and a success otherwise. The aggregate `check` job passes only when `changes` succeeded and every gated leg passed, or no leg was gated. That job is the check the main ruleset requires.

`ci.py check` is a quick run before a push, never a gate: it plans the check tier against the merge base with `origin/main`, uncommitted and untracked files included, and runs the touched jobs that compile and test nothing, so nothing goes to Boat. Clippy, the fuzz build, every Rust job and the jobs marked `ci-only` are left to CI, and named so; CI already runs them, and repeating them first only delayed every push. Every command runs with `PYTHONUTF8=1`, so Python tools read and write their pipes as UTF-8, and a job's `unset` drops environment variables that would change what it runs.

UI tests are one job, not split per test file. Tests read stylesheets, sources, configuration and fixtures outside their import graph, including files under `crates/`, so a narrower gate would skip tests a change had broken. A check script added to `tools/` must be a job in the pipeline. A test fails while any `tools/check-*.py` is missing from it.
