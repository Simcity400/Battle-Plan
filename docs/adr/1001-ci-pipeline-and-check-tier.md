# 1001. One pipeline definition, reused by input hash, with a per-change check tier

Verification is one pipeline, `tools/ci.toml`, run by one entry point, `tools/ci.py`. Each job declares its tier, its toolchain, its inputs as path globs and its command. The same definition serves this machine today and a hosted runner later: nothing in it names this machine, the store's location comes from `HOI4_CI_STORE` or the main checkout, and the commit status goes through the GitHub CLI. The shape follows T3 Code's `ci.yml`. A `changes` step first gives each job its gate, then the jobs run in parallel with Boat jobs first, and one aggregate verdict follows. The check tier (`ci check`) is what an agent runs on a finished change. `ci main` runs the check and main tiers on a commit already on `origin/main` against its parent, and posts `ci/main`: a poller runs it on each push to main. Tiers are ordered as `tools/ci.toml` lists them, and each runs the jobs of the tiers before it. The nightly and release tiers are declared so jobs can name them. The main poller, the nightly re-plumbing and release promotion are separate work.

The gate is GitHub's hosted CI, `.github/workflows/ci.yml`, which the public repository runs at no cost on pull requests and on each push to main. Its `changes` job runs `ci.py changes`. That plans the tier from the files alone: the crate graph comes from the manifests, no toolchain is asked, and nothing is reused. It writes a matrix of the job groups with work, as `tools/ci.toml` assigns them. Repository checks and UI run on Linux. Tool tests, the feature-unification check, browser tests and Rust run on Windows, because Cargo resolves features for the host and the workspace's are Windows'. The runner label for each group is fixed in the workflow, never taken from the matrix, so a pull request cannot choose a self-hosted runner. Each matrix leg runs `ci.py job --group --jobs`, with the job names `changes` planned. A planned job that the leg would not run fails the leg, so a gated job never passes by being skipped. The job list has one source. A Rust job runs its `hosted` command there: Clippy through `check-clippy.py`, and nextest, both with Cargo on the runner and `rust-cache`. The cache is saved only from pushes to main, and third-party actions are pinned to commits. Boat is never used there and never stands in when that CI fails. Nothing is held, paused or deferred on a hosted runner. A workspace-wide change runs the workspace's tests. The aggregate `check` job passes only when `changes` succeeded and every gated leg passed, or no leg was gated. That job is the check the main ruleset requires. Superseded pull request runs are cancelled by the workflow's concurrency group. Each push to main has its own group (its run id), so a later push never replaces a pending one. A push compares with the exact tip it replaced, not their merge base, so a force-push that drops a commit still runs that commit's jobs; the workflow fetches that tip when the clone lacks it. A newly created main compares with the empty tree, and its ratchets compare with HEAD's first parent, or are not run without one. A ratchet's own merge base with a rolled-back tip is HEAD itself. That code already passed on main's history, so nothing new is ratcheted. `changes` fails if it cannot plan a job, and `check` fails without an explicit gate decision. A job's definition includes its group's settings. A change to the pipeline's implementation (`tools/ci.py`, `tools/ci.toml`, the workflow) runs every job, Rust across the workspace. A change to a job's `shared` scripts runs it widely, and `keyed` files (Boat's scripts for local runs) only invalidate its passes. An unreadable crate graph makes a Rust job not run, never skipped, whenever its gate could be needed. The tool tests' toolchain is the Python version together with the PyYAML and Tree-sitter versions they import. A file in a crates job's `widen` list, such as the nextest configuration for the Rust tests, makes the job workspace-wide. The local status goes to the repository the `--upstream` remote points at, `refs/remotes/` included; an upstream naming no GitHub remote is not posted. Locally, `ci check` runs the same jobs with Rust on Boat and reuse, and its `ci/check` status is the agent's convenience, not the gate.

A job's result is stored under a hash of everything it reads: its definition, its toolchain (the version command's output and the toolchain's files, such as the lockfile), its input files as Git blob ids, and the base revision for a ratchet that compares against it. A job whose hash has a recorded pass is reused and reported with the commit that passed it. A job none of whose inputs changed since the merge base is skipped, not passed. Each file's entry records whether Git tracks it, so a pass recorded while a file was untracked never stands in once that file is committed. Repo checks that list tracked files would not have read it. A rename counts as a change at both paths. A job whose definition, or its toolchain's, differs from the base's pipeline runs even if no input changed. A run records its passes only if HEAD, every file hash and every file's modification time are unchanged when it ends. An edit made while Boat compiled, even one undone before the end, is therefore never certified under the old hash. Folder times are left out because running a job creates caches such as `__pycache__`. A move made and undone in the middle of a run, with the files' times preserved, is not detected. The node toolchain's digest includes the installed `node_modules/.package-lock.json`. An installation that `npm ci` would not reproduce is a missing toolchain, and its jobs are not run. That covers several cases:

- the dependencies in `package.json` differ from the lockfile's;
- a package is installed at another version or from other contents;
- a locked package is absent (optional and peer packages may be absent);
- a package is installed but not locked;
- a locked package's own `package.json` is absent or at another version on disk, or a top-level package on disk is not locked;
- `npm ci --dry-run --offline` refuses the manifest and lockfile, for example over an override the lockfile lacks. It runs on copies of the two files and any `.npmrc` in a scratch folder, so it reads nothing installed and changes nothing in the worktree.

The end-of-run snapshot also covers the installed lockfile's content and modification time, so an install made during a run invalidates it. A sparse checkout is refused, because the index lists files it leaves out. A job whose tool is absent, such as Cargo for the feature-unification check, is not run either, instead of failing.

Three granularities keep reuse useful. A `command` job is one hash. A `files` job hashes each file with its shared inputs. Changing a shared input, such as the scanner itself, rescans every file with the job's `whole` command when it has one. Otherwise only changed files without a pass are scanned, in batches that fit a Windows command line. The citation scan is a `files` job, and `git grep` now includes untracked files so a new file cannot escape it. A `crates` job hashes each workspace crate as its own folder plus the folders of every workspace crate it reaches through any path dependency, including dev-dependencies, together with its shared inputs (the Boat runner scripts). Those invalidate its passes but select no crates. It selects the changed crates and their direct dependents, from `cargo metadata --no-deps`. A change to the toolchain files (root manifest, lockfile, toolchain, Cargo config, vendored crates, `test-unify`) is workspace-wide. Clippy then checks the workspace, and tests are left to a later tier. So does a changed definition of a `crates` job, because no crate selection would exercise it. Tests also leave a selection above the job's `limit` to a later tier. Reading a file outside those folders at build or test time is not tracked. The later tiers' full runs cover that.

UI tests are one `command` job, not reused per test file. Tests read stylesheets, sources, configuration and fixtures outside their import graph, including files under `crates/`, so an import-closure key would reuse results that a change had made stale.

Every Rust compile runs on Boat. `boat.py clippy` is the remote `check` path with Cargo's `clippy` subcommand, so it shares the check VMs' dependency metadata, and Clippy replaces `cargo check` in this tier. It runs through `tools/check-clippy.py`, which fails only on findings in lines the change writes, so its crate keys include the base. Boat's test path builds test programs on the VM and runs them on this machine. That makes the Rust test job heavy local work. It is skipped if either game lock under `%TEMP%` (the agents' or the smoke run's) exists when the run plans it or when it starts. A game started while Boat compiles is not seen before the test programs launch. It is not run at all while `[local] heavy = "paused"`, which is set while other measurements need this machine. Both are reported by name and neither counts as a pass. Boat jobs start first and every other job runs alongside them, each command in a job object below normal priority. The command starts suspended and joins its job before it runs, so nothing it starts escapes unless it asks to. Breakaway stays allowed because the warm-target refresh is meant to outlive the command that starts it. A first Ctrl+C reaches the commands and waits for them, so Boat can release its VM. A second ends them with their jobs. A Boat exit 75, including a VM that cannot install Clippy, is reported as not run. A job's `unset` drops environment variables that would make it compile here, such as the warm-target end-to-end switch. Every command runs with `PYTHONUTF8=1`, so Python tools read and write their pipes as UTF-8. The comment check's toolchain is its pinned Tree-sitter versions. A toolchain's `probes` put the path and the reported version of optional tools on PATH into its key, such as `actionlint` for the workflow check, which runs it only when present. If `tools/ci.toml`, or a file the npm consistency check copied, changes before the first snapshot, the run stops.

The verdict is a failure if any job failed, and an error if a job that should have run could not, such as a missing `node_modules` or a Boat failure. It is pending if a job of the tier was held for the game, paused, or deferred to a later tier, such as Rust tests for a workspace-wide change. It is a success only when every job passed, was reused, or was skipped because its gate was not needed. Every job that is not a plain pass is named in the status. A new run of the same tier on the same branch (or, detached, the same worktree) supersedes an older one still running. It claims the branch before it plans. The older run sees this while it waits, after its jobs end, and again just before posting. It ends only the local commands it started itself, lets its Boat commands finish so they release their VMs, and records and posts nothing. The verdict is posted through `tools/commit_status.py` as the commit status `ci/<tier>`, only when the worktree is clean, so the commit is what ran, and, for `ci check`, only when the run compared against the merge base with `origin/main`, so a narrower comparison cannot replace the change's verdict. For `ci main`, it is posted only when HEAD is on `origin/main` and the base is not HEAD itself. A status that cannot be posted turns success or pending into exit 2. Exit codes are 0 for success, 1 for a failure, 2 for an error, 3 for pending and 4 for superseded. A status GitHub refuses for a commit it has makes the run exit 2. A commit GitHub doesn't have yet is reported, and after a push the rerun is reuse. Each run writes per-job timings, its verdict and whether it exceeded its tier's budget to the store. The time covers the final snapshot and the pass records too. Two worktrees may record the same pass at once. Windows then refuses the second replacement, and the record already there stands. Pass records and runs expire after 30 days. An expired record is never reused, and pruning happens once a day, and only folders older than that are removed.

A check script added to `tools/` must be a job in the pipeline. A test fails while any `tools/check-*.py` is missing from it.
