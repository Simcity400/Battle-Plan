# 1001. One pipeline definition, run only on GitHub's hosted runners

Verification is one pipeline, `tools/ci.toml`, run by one entry point, `tools/ci.py`. Each job declares its tier, its toolchain, its inputs as path globs and its command. GitHub's hosted CI, `.github/workflows/ci.yml`, is the only test runner and the only gate. The public repository runs it at no cost on pull requests and on each push to main. Nothing runs tests on a maintainer's machine, and Boat is only the agents' development compiler: it is never used in CI and never stands in when CI fails. The shape follows T3 Code's `ci.yml`: a `changes` job gives each job its gate, the legs with work run in parallel, and one aggregate `check` job gives the verdict. There are two tiers, as `tools/ci.toml` orders them: `check` for pull requests and `main` for pushes to main; a later tier runs the jobs of the earlier ones, and a job of a later tier that would run is left to it.

`changes` runs `ci.py changes`. It plans from the files alone: the crate graph comes from the manifests and no toolchain is asked. A job none of whose inputs changed since the base is skipped, never reported as passed. A `files` job scans the changed files that match, or every file, with its `whole` command when it has one, when the change is wide; long lists are split into command lines that fit Windows. A `crates` job selects the changed crates and their direct dependents. A change is wide for a job when its definition differs from the base's pipeline (a definition includes its toolchain and group), or a file it always depends on changed: its toolchain's files (for Rust the root manifest, lockfile, toolchain, Cargo configuration, vendored crates and `test-unify`), its `shared` scripts, the files in its `widen` list such as the nextest configuration, or the pipeline's own implementation (`tools/ci.py`, `tools/ci.toml`, the workflow). A wide `crates` job takes the workspace. An unreadable crate graph makes a Rust job not run, never skipped, whenever its gate could be needed, and `changes` fails if it cannot plan a job; `check` fails without an explicit gate decision. A pull request runs the Rust tests for the changed crates and their direct dependents only, and Clippy for the changed crates alone (`dependents = false`): a dependent's lints cannot change when its own source did not, Clippy fails only on lines the change writes, and the tests compile every dependent. A push to main runs every job across everything it covers, whatever changed, so main's verdict, which releases wait for, is never a skip; its Rust jobs say how many crates lie beyond a pull request's scope, and a failing test in one of them is marked so. Reading a file outside a crate's folder at build or test time is not tracked; main's whole-workspace run covers it.

The matrix has one leg per group for its ordinary jobs. Repository checks and UI run on Linux. Tool tests, the feature-unification check, browser tests and Rust run on Windows, because Cargo resolves features for the host and the workspace's are Windows'. The runner label for each group is fixed in the workflow, never taken from the matrix, so a pull request cannot choose a self-hosted runner. A job with `shards` (Clippy and the Rust tests) gets legs of its own, at most that many, so the two run beside each other. `changes` splits its crates from the workspace graph and each crate's committed Rust source size: the costliest crate first, each to the leg it adds least to, counting a library once per leg, so a crate joins the leg already building its dependencies. A change gets a share of the legs in proportion to its cost against the whole workspace's. Each leg runs `ci.py job --group --jobs`, with `--shard AT/COUNT/DIGEST` for a sharded job, and plans again. A planned job that the leg would not run fails the leg, so a gated job never passes by being skipped, and a leg whose own split of a job differs from the one `changes` digested fails too, so no crate falls between legs.

Each Rust leg restores one cache per job: the registry and the whole target folder, workspace crates included. A workflow of its own, `rust-cache.yml`, writes it after each CI run of a push to main, so it never delays main's verdict or a release, which waits only for the push's own workflows; it runs only for this repository's pushes and always builds main's newest commit, whichever push's CI run finished, so an older run finishing late never builds an older pipeline. It runs the job's `warm` command across the workspace, skipping the build and the save when no crate or Rust toolchain file changed since the folder's commit; a newer cache run waits for a running one rather than cancelling it. Only a build that succeeded names HEAD in the folder as the commit it was built from and is saved; a failed one saves nothing, because its folder mixes units rebuilt at HEAD with the commit it named before. A successful build also removes every unit it did not use, found from Cargo's JSON messages, so a unit that comes back later (a feature or profile setting changed and changed back) is built again rather than found fresh against sources it never saw, and it removes the executables, which no leg reuses and which would not fit the cache. Cargo decides freshness by file times, and a checkout makes every file new. So before Cargo runs, `ci.py times` sets every tracked file and folder to one fixed old time, except the paths that differ from the commit the folder was built from and the folders above them, which are now. A file added or removed makes every file of its crate's folder now, because a new file can change how a crate compiles without being in any unit's dep-info. Cargo then rebuilds exactly the crates whose files differ and those above them, and keeps third-party crates, which it keys by version, not time. A folder that names no commit the clone has makes every file new. A build script that watches no file would compare a stored time instead, so `test-unify`'s watches its own source. The C code that build scripts compile is not rebuilt when only the runner image's compiler changes, as with Cargo anywhere. The cache key holds the lockfile, toolchain and Cargo configuration and the commit. A pull request falls back to the newest cache of any lockfile; the cache workflow only to one of its own. sccache was removed after it showed no speed-up. Third-party actions are pinned to commits, each with a `# vX.Y.Z` comment so Dependabot's grouped github-actions updates can move the pin and its version together. The comment ratchet exempts exactly that comment after a SHA-pinned `uses:` in a workflow.

Clippy runs through `tools/check-clippy.py`, which fails only on findings in lines the change writes. Ratchets compare with HEAD's merge base with the base, so a rollback or force-push ratchets only what HEAD adds to their shared history: restored code already passed there. Hosted runners have no game installation. The tests build with Cargo's `ci` profile and run with nextest's `hosted` profile, which writes a JUnit report, and `ci.py` sorts the failures in it. Every test runs without the game, against the `synthetic-game` crate, except the dashboard crates' (`dashboard`, `dashboard-base`, `dashboard-core`, `dashboard-text`), which need the install until the dashboard rework (issue #169). A failure in one of those crates' test binaries is reported as not run there, under a `not-run` rule of `rust-test` that names the crates and cites the issue, never as passed, and only when three things hold. Nextest reports libtest's plain panic exit. The last panic on the test's own thread is, in full, a missing-install message: the game fixture's named `NotFound` cause, or a direct read's bare `expect` (the rule's `panic`). In any other crate the same panic is a failure. And the test reported no error after it. A test that needs the game reports that by panicking, never by returning early as a pass. A timeout, an abort, leaked handles, or any other panic or error fails the job, and the leg prints every such failure with its output and uploads the JUnit report. The override also needs nextest's summary to show every selected test run, so a cancelled run never passes. The profile stops a test after 10 minutes. The desktop acceptance suite (`tools/e2e`) against a recording has no runner in CI.

Superseded pull request runs are cancelled by the workflow's concurrency group. Each push to main has its own group (its run id), so a later push never replaces a pending one. A push compares with the exact tip it replaced, not their merge base, so a force-push that drops a commit still runs that commit's jobs; the workflow fetches that tip when the clone lacks it. A newly created main compares with the empty tree, and its ratchets compare with HEAD's first parent, or are not run without one. The verdict is a failure if any job failed, an error if a job that should have run could not, and a success otherwise. The aggregate `check` job passes only when `changes` succeeded and every gated leg passed, or no leg was gated. That job is the check the main ruleset requires.

`ci.py check` is a quick run before a push, never a gate: it plans the check tier against the merge base with `origin/main`, uncommitted and untracked files included, and runs the touched jobs that compile and test nothing on the machine. Clippy runs through its `local` command on Boat; the jobs marked `ci-only` and Rust jobs without a `local` command are left to CI, and named so. Every command runs with `PYTHONUTF8=1`, so Python tools read and write their pipes as UTF-8, and a job's `unset` drops environment variables that would change what it runs.

UI tests are one job, not split per test file. Tests read stylesheets, sources, configuration and fixtures outside their import graph, including files under `crates/`, so a narrower gate would skip tests a change had broken. A check script added to `tools/` must be a job in the pipeline. A test fails while any `tools/check-*.py` is missing from it.
