# 1397. Per-widget playback cost, the weak-machine profile, and placeholder failures

The acceptance suite measures dashboard playback on a reproducible weak-machine profile (`--profile weak`: four cores and 4× CPU slowdown; `--profile weak8`: four cores and 8×). Core confinement is enforced at the OS scheduler via `JOB_OBJECT_LIMIT_AFFINITY` on the app's Windows Job Object, which inherits to every WebView2 child process (`msedgewebview2.exe`), and verified before close via `JobObjectBasicProcessIdList` and `GetProcessAffinityMask`. Because Chromium on Windows reads `GetSystemInfo` rather than process affinity for `navigator.hardwareConcurrency`, the sweep also applies `Emulation.setHardwareConcurrencyOverride` before opening the campaign so the page sees the confined processor count and creates `clamp(cores - 2, 1, 4)` drawing lanes. The report header states both measured confinement and what the profile does not imitate: graphics card performance, memory speed, and native Rust/IPC decoding.

Per-widget playback cost (`--phases widget-costs`) mounts each registered widget kind alone at its default size on a dedicated page, preceded by an empty page baseline, and plays each at 1,440 game hours per second for a fixed window under the chosen profile. Measuring alone avoids cross-widget interference and keeps all 114 kinds well under an hour by reusing one session and flushing the perf log between widgets instead of re-reading the entire log per widget. Each kind is ranked by `max(0, mainDelta.p95) + worker.p95` (net main-thread p95 frame time above the empty page plus drawing-lane serve time p95 on changing frames) so both main-thread and worker costs count in one millisecond-per-frame metric. Results are written to `widget-costs.json` and a sorted table in `e2e.md`.

The `Heaviest` fixture page places the N most expensive kinds from `widget-costs.json` (default 30) packed at minimum size into one 4K screen view with zero scrolling, played at 1,440 h/s and judged against 60 presented frames per second, freshness, and exact reads. Any placeholder, refusal, or error on a dated playback page fails by name. A visible "isn't playing back yet" placeholder always fails its row with reason `not migrated`, while keeping the visual distinction between `not migrated` and a real failure so migration progress remains visible.

To baseline unmigrated widgets before they are migrated, `ui/vite.config.ts` defines a build-time constant `__BATTLEPLAN_MEASURE_UNGATED__` that is `false` in every normal build (dead-code-eliminated) and `true` only when `suite.py build-ui --ungated` sets `BATTLEPLAN_MEASURE_UNGATED=1`. No runtime flag exists, and any run using an ungated bundle displays a prominent banner in `e2e.md`.

Individual input checks in `playbackInputs` and individual scroll/speed windows in `playback` record their own failures and clean up instead of aborting the phase. Perf log losses are scoped by time overlap to the windows they affect; any window overlapping dropped records fails rather than passing.
