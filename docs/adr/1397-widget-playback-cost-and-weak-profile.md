# 1397. Per-widget playback cost, the weak-machine profile, and placeholder failures

The acceptance suite measures dashboard playback on a reproducible weak-machine profile (`--profile weak`: four cores and 4× CPU slowdown; `--profile weak8`: four cores and 8×). Core confinement is enforced at the OS scheduler via `JOB_OBJECT_LIMIT_AFFINITY` on the app's Windows Job Object, which inherits to every WebView2 child process (`msedgewebview2.exe`), and verified before close via `JobObjectBasicProcessIdList` and `GetProcessAffinityMask`. Because Chromium on Windows reads `GetSystemInfo` rather than process affinity for `navigator.hardwareConcurrency`, the sweep also applies `Emulation.setHardwareConcurrencyOverride` before opening the campaign so the page sees the confined processor count and creates `clamp(cores - 2, 1, 4)` drawing lanes. CPU throttling applies across all measured JavaScript phases (`pages`, `pages-at`, `glance`, `seeks`, `catalogue`, `controls`, `playback`, `widget-costs`, and browser traces) and is restored after each phase; native GPU viewer phases (`map`, `mapfps`) are core-confined without JS throttling. Every session's own Job confinement, `hardwareConcurrency`, and drawing-lane count are verified individually and fail the Cold sessions table if any check misses. The report header states both measured confinement and what the profile does not imitate: graphics card performance, memory speed, and native Rust/IPC decoding.

Per-widget playback cost (`--phases widget-costs`) mounts each registered widget kind alone at its default size on a dedicated page and plays each at 1,440 game hours per second for a fixed window under the chosen profile. Measuring alone avoids cross-widget interference and keeps all 114 kinds well under an hour by reusing one session and flushing the perf log between widgets instead of re-reading the entire log per widget. Because `Dashboard` preloads all widget renderer chunks via `requestIdleCallback` on mount, measuring the empty page cold right after opening the campaign catches idle chunk compilation spikes in the baseline. The harness therefore waits on `CostEmpty` for widget chunk resource entries to settle, runs a short warm-up play at 1,440 h/s, and measures the empty-page baseline twice—once before the first widget (`start`) and once after the last (`end`). Both samples and their spread are reported; if either sample loses records, misses 1,440 h/s coverage, has fewer than 30 frames, has a tail gap (`p95 - p50`) over 15 ms, or drifts across the pass (`Δp50 > 3 ms` or `Δp95 > 8 ms`), the baseline fails by name and no widget receives a numeric `costScoreMs`.

Each measured kind is ranked by `costScoreMs = mainDelta.p95 + worker.p95` (net main-thread p95 frame time above the pooled empty-page baseline plus drawing-lane serve time p95 on changing frames). Both `Δp50` and `Δp95` are reported as separate columns beside raw `Main p50` and `Main p95`. Negative deltas are never silently clamped to zero: they are shown as negative and marked `below baseline noise`. Rows with incomplete windows, lost perf records, stopped clocks, zero timed frames, or an unusable baseline receive `costScoreMs = null` instead of zero; rows with fewer than 30 timed frames report their exact frame count and window duration and are flagged as low-sample. Results are written to `widget-costs.json` and a sorted table in `e2e.md`.

The `Heaviest` fixture page places the N most expensive measured kinds from `widget-costs.json` (default 30, refusing to run if fewer than N measured kinds exist) packed at minimum size into one 4K screen view with zero scrolling, played at 1,440 h/s and judged against 60 presented frames per second, freshness, and exact reads. Any placeholder, refusal, error, loading state, or blank body observed during a dated playback window fails by name; errors are classified as refusals only when positive refusal text matches, never by button presence. A visible "isn't playing back yet" placeholder always fails its row with reason `not migrated`, while keeping the visual distinction between `not migrated` and a real failure so migration progress remains visible.

To baseline unmigrated widgets before they are migrated, `ui/vite.config.ts` defines a build-time constant `__BATTLEPLAN_MEASURE_UNGATED__` that is `false` in every normal build (including `production` mode regardless of environment variables, so dead-code elimination removes the branch) and `true` only when `vite build` runs in the dedicated `--mode measure-ungated` mode via `suite.py build-ui --ungated`. `build-ui` refuses to overwrite a repo path or any existing non-empty directory that lacks its `.battleplan-ui-bundle` marker. No runtime flag exists, and any run using an ungated bundle displays a prominent banner in `e2e.md`.

Individual input checks in `playbackInputs`, the optional `idleCost` sample, and individual scroll/speed windows in `playback` record their own failures and clean up instead of aborting the phase or discarding completed window measurements. Perf log records are scoped by session, and perf log losses are scoped by time overlap to the playing, input, and idle windows they affect; a playing-window loss fails every placement in that window rather than counting any as passed.
