# Resolve game-site keys from the verified image

`Rva` identifies a position in the reference build. Production readers enter pending mode before installing a located image, and synthesize addresses from keys only in test mode. Off-image consumers map the file at its virtual section extents and resolve stored pointers relative to the target module base. A previously installed table can be reused for the same file identity and base. Lookups can outlive a replacement, so published tables stay allocated. [Image and key API](../../crates/engine-sites/src/lib.rs) · [PE image views](../../crates/engine-sites/src/image.rs)

`Image::live` reads a loaded PE32+ module only through the caller's guarded copy. It copies the headers, then copies each range the locator asks for, bounded by its section's virtual extent, and never borrows the mapped image: sections can hold data other threads write, and a page that cannot be read withholds that range. `install` is the only writer to the published table pointer. It leaks each new table before publishing it with release ordering, so an acquire load in `located` can borrow any published table for the life of the program, including one that has been replaced. [Module view](../../crates/engine-sites/src/image.rs) · [Published table](../../crates/engine-sites/src/lib.rs)

The generator and Rust locator share a fingerprint format. The input length precedes little-endian words and a zero-padded tail. Relocation fields are zeroed, including when they straddle words. Unique unwind-range fingerprints seed the search. The remaining functions and globals are reached through validated relative operands, vtable slots and chained ranges. Every incoming edge must agree, including those discovered after the target was placed. A function whose original operands disagree is withheld and the search is repeated without relying on it as evidence. Targets of masked operands must identify the same part as in the reference build. [Fingerprint](../../crates/engine-sites/src/fingerprint.rs) · [Locator](../../crates/engine-sites/src/locate.rs)

Vtable identity uses the type and subobject. Its slot count is checked before following any slot. The locator still uses the identified table to verify operands when the slot count separately withholds the table. Known image hashes identify executables checked against this source. Elsewhere, unchanged constructor and vtable-shape witnesses verify layouts. A changed witness that applies to the overall layout vetoes it. The witness test permits tables that lack that evidence to be withheld and separately checks the installed reference image with its checked-layout status. [Locator](../../crates/engine-sites/src/locate.rs) · [Reference-build test](../../crates/engine-sites/tests/reference_build.rs)

Hook callers use bytes saved during successful location, including relocated operands and verified bytes at the end of a range. A key can name an interior position, such as the instruction after a call. Interior references use the containing verified function's range and diagnostic. An address inside a verified function cannot be a match for a key from an unlocated function. Other unknown candidates keep the classification unproved. `at` and `which` mark a table scope with its first withheld key so a failed lookup cannot silently appear as missing data.
