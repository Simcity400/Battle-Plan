# 1121. Keep the embedded map window and its renderer on separate threads

The desktop app owns and pumps each native map window. The map runs inside the app process but draws on a separate thread, using in-process desktop protocol channels and the host's existing data service. The window procedure translates native input to egui events for that thread. Capture, focus and retirement requests post back to the window thread. The acceptance tools find a child by its stable title. The harness can create and pump a top-level window while exercising the same rendering path. Its window dumps and paced runs present through a real swap chain.

A close requests that the map stop. The map releases its rendering resources and surface before the window thread destroys the handle. The driver drops the resources that drew on a device before releasing that device and its surface under the lifecycle lock. Panic containment records the original panic location, which a caught payload does not provide. A device-loss reason takes precedence over subsequent errors or exits. Restart creates a new device and surface, so device-keyed caches must exclude old resources even if a cache still retains them.

Native input uses physical positions for spatial controls, including the position of W on a US keyboard for forward motion on other layouts. Alt system combinations stay with the top-level window. When focus moves to the map, it reads the current modifiers because those keys may have been pressed while the dashboard owned the keyboard. Frame pacing follows the display under the window. The optional frame-rate limit holds the frame until its own next deadline and preserves the input that requested it.

The renderer keys shared state by weak renderer identity, so address reuse cannot associate a new renderer with retired state. Render work completes at its call sites to preserve cache registration and paint order. Stage the frame before acquiring its swap-chain image to put the wait at the end of preparation. A hidden or unpresented frame can still carry egui texture updates. Acquisition failure that invalidates the configuration leaves reconfiguration to the next frame and retains those updates. The performance harness can draw into a reusable window-size texture while waiting for desktop composition, which isolates the cost of presenting the map. Tests keep managed texture lifetime ordering separate from checks of the renderer's registered native IDs.

In `map_device`, the surface borrows the host window's raw handle. A close requests the map thread to stop and `Window::destroy` retires the window only after the map thread has dropped the surface. `Window::create` registers the class with this module's procedure. In `window_proc` the link pointer is a window-owned strong reference from `WM_NCCREATE` through `WM_NCDESTROY`, accessed only on that window's thread. For a message with an associated Win32 structure, its documented pointer remains valid for the call.

`Window::destroy` posts retirement and can tolerate a failed post to an already retired handle. `focus` and `capture` post to their own window. `metrics`, `shown`, `send_to_back` and `points` use the established window handle for placement, DPI and visibility. `modifiers` reads the calling thread's key state. `pump` dispatches that thread's messages and test `dispatch_posted` drains them without waiting. The close and focus tests send messages to their own test windows and read their own thread's keyboard state.

`paint_unpresented` calls `DwmFlush` at the compositor boundary. It supplies no handles or storage, and the call waits for the next composition before measurement continues.
