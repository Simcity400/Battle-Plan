# 0302. Evaluate followed dashboard queries on the playback stepper

Follow uses the product request the dashboard would send at the head. If the recording and clock mapping have no playhead, or its tables cannot answer a query, the service refuses it by name and the widget can continue requesting the product. Tracks that map the same timeline to different clock offsets have separate follow routes. A route identifies one playhead throughout its lifetime. Seeking keeps subscriptions and starts an epoch whose reset sends full answers again. Closing a recording removes its subscriptions. The host takes anchors from the UI unless a visible map already places the playhead.

At each step boundary the hook takes subscription changes and declares the union of needed columns to the playhead. It re-evaluates a query only when its columns and rows were touched, its table changed status or reset, or a requested tag's holder changed. Unchanged answers can share the step's confirmed hour without another payload. A live query fixes its keys for the lifetime of that structure. It sends the whole row set initially, after a reset, or after data returns from an unrecorded span. Subsequent messages replace changed rows by key. A renumber invalidates cached slots. A patch with a key outside the previous answer cannot be merged with it. Heads such as command-stream products have their own data source. They run on the stepper on every step, including gaps, and use the same deduplication as followed tables.

The feed of a log table receives every appended row with its insert hour, including rows forgotten within the step. The feed of a state table instead asks for passing rows. A standing list of a log gets its live ordinals, fetches their cells in the background, and folds in appends and forgets across subsequent steps. A gap has no logged appends and supplies a named missing answer to state queries. Rankings exclude missing values. An owner series ties by tag bytes, a row ranking by key, and a part ranking by the part key. Rejections report the table or column and keep the recorded reason text where available. A reason can be cached by run and ID to name it between parts, where the current part has no string to read.

Panels read whole tables at their requested cadence and offer the newest complete frame without blocking. A source which stops sends the panel a dated stopped record with its reason, shown as a failure, never as missing data, and cleared by the next reading. A panel groups live cells into one followed query per table and set of source columns and keeps a group's follow ID while those columns and keys are the same. A separate ID bit distinguishes panel cell subscriptions from client subscriptions. The numerical formula is a value, sum, difference or ratio times a scale. A zero divisor leaves a value missing. The binary path preserves every signed 64-bit integer. Panel JSON uses JavaScript numbers. The on-demand path seeds the same cells at the requested hour and uses the same named missing states.

The binary answer is little-endian and aligns its sections to eight bytes so the UI can read numbers in place. Its header holds the magic, flags, confirmed hour, answer count, page seek and clock offset. Flag bit zero marks a reset, and the higher bits name the follow route. Each answer is framed by its ID, read hour, body length and a zero field. The body starts with a kind byte, three zero bytes, and the row, column and text counts. Kind zero carries a named refusal. The other kinds carry keys as low and high 64-bit halves, signed 64-bit cells in row order, cell states, and text indexes for the reason and name of each row. The append kind also carries the insert hour for each row. Texts are length-prefixed UTF-8. Kinds one through three carry a whole row set, appends and changed rows respectively.

Follow answers and dated panels share an outgoing pipe. Each little-endian frame starts with a 32-bit payload length, the message kind, a continuation byte, two zero bytes and a 32-bit sequence. A fragmented message repeats kind and sequence through its final frame. A failed output stops the queue and publishes its reason. Offers do not wait for the pipe. The shared budget accounts for hosted read-ahead rings and outgoing queues. Merge keeps the latest answer for each ID on one route, overlays changed rows, and preserves a reset. The queue sends both messages when they cannot merge.

A dated panel message identifies its clock, native route and seek. A record carries a dated reading, refusal or confirmation and can be forwarded with its padding intact. The follow hook updates its retained-size sample periodically and after subscription changes.

The optional follow and log microbenchmarks measure stepper work, validate sampled answers against reads at the same hour, and can compare the order of a feed's delivered rows with its table. They support flat and paced playback, page sizes, explicit seek patterns and synthetic log shapes to isolate specific costs. Their CLI arguments and outputs are implemented by the benchmark binaries.

The follow benchmark's selection file declares one table per line, with no column suffix for every column, `:numeric` for numeric columns, or a colon and comma-separated names for explicit columns.

Tests compare applied table heads when a part read stalls the clock. The harness lets the table catch up and ignores steps from earlier epochs until the reset arrives. Its log standing-list test uses the single ordered fetcher to synchronize ordinal reads with the first newly built step that can consume them. Subscriptions may join after lead has filled. Rust answer fixtures covering every wire kind are also read by the TypeScript follow tests, which guards the cross-language layout.
