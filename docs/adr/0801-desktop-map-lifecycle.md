# Keep desktop map work outside the window event loop

The dashboard reads the host's data service directly. Native maps run on their own threads and share that service. A map's failure leaves dashboard data available. A content refusal leaves recording-only queries available. Binding uses the recording's own executable tables. An unavailable installation can bind again when its folders return, and applying the same folders retries the binding. A transient service refusal starts with the service's recognized reason so the frontend can retry.

Host commands check framing and pass JSON through for one parse in the frontend. The native reader performs bounded fragment assembly and passes complete replies to their awaiting commands. If a source-open response is abandoned, a cancellation rolls back a lease the native side may already have created. A followed query goes to the native playhead. Revision checks, recording upgrades, and recorded file reads run outside the window pump, with the upgrade before the revision check so it identifies the recording being opened.

A native viewer owns a child window created and pumped by the desktop app. Its startup thread reads preferences outside the host lock because window getters can wait on the main thread and preference resolution can itself read host state. Saved changes received during launch supersede the launch-time preferences. Display choices are numbered and overlaid by kind only when sent after launch began. Short-lived requests to reread saved settings coalesce; a starting viewer still receives a pending request. Coalesced camera choices keep the action queue available for other controls. Bounds updates alone never start a viewer.

The main map and dashboard map surfaces use an explicitly selected geometry owner. Late cleanup from the other owner cannot hide the active surface. The renderer and its native window serve one dashboard geometry snapshot, including hidden views. Opening a recording in analytics keeps only its latest map request until a map surface becomes visible. A viewer end preserves unacknowledged recording requests or restores the last shown position. A lost GPU device allows one restart from the displayed state after readiness. An earlier failure reports why and awaits a new start. A replacement viewer begins without the previous viewer's camera or controller state.

Map events and exports are correlated with the running viewer generation. An export is registered and queued under one lock, then completes once on the actual save, refusal, or viewer end. A closing viewer may still finish its own export. Unsatisfied exports are refused when their viewer ends, and any unsent ones are withdrawn. A pop-out export identifies the window before entering the save dialog. Host state is published in mutation order, and the pop-out owner publishes status for its window.

On exit the main event loop keeps pumping while an external thread stops the viewers. Each surface is released before destroying its parent window. The data service stays available until map shutdown so loads can finish. A fallback ends the process while the window still exists if orderly shutdown cannot ensure that drawing has stopped.
