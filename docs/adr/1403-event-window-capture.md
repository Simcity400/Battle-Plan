# 1403. Event window decisions and presentations

## Context

The event feed recorded each fired event and the option chosen, but not whether the recorded player's client asked for a window, nor what that window showed. The product rebuilt titles and options from the authored content, which is exact only where the text has no scripted parts and no option has a trigger.

The game decides the window in one place: the routine that fires an event for a country tests, in order, whether the recipient is AI-controlled, whether the event is hidden, whether the recipient is the viewing country, whether the actor is the recipient of an event that does not fire for its sender, a per-player restriction to major events whose options carry no trigger, whether the pending instance is new, and whether its window is already open. Only then does it queue a window request. The game's interface thread later builds the window from the queued scope copy: it resolves the title, the picture key, each admitted option's label (or one fallback button when none is admitted) and the description, then applies the user's popup settings, which can leave the built window hidden, and registers it as open. An interface reload builds it again with the same scope.

## Decision

- **Decisions** are witnessed by taps at relocatable instructions along the gate section of the fire routine and resolved at its common exit. The taps keep a per-thread trace keyed by the routine's frame and write the store once per firing, so the added store traffic stays one access per fired event. The AI and hidden gates share one exit that no tap separates, so a hidden event that reached it is `HiddenOrAiControlled` and never guessed further. A decision is published only for a firing whose section finished; an unfinished one stays "not recorded".
- **Presentations** are witnessed by taps where the build hands each final string on, assembled per window and published at the commit point, which also reads the popup-setting result. Each field is copied and verified independently: an unreadable title, picture or option label withholds only that field. The interface thread never touches the event-feed store; it pushes into a small queue that the feed's hourly seal moves into the hour's row, and a discarded publication marks the next interval's presentations lost rather than complete.
- **Storage.** Decisions travel as `(occurrence sequence, decision)` pairs and presentations as a list in one appended `windows` field on `EventFeedHistory`, so the fired-event encoding is unchanged. The feed derivation adds a `window` column to `FeedEvents` for script and news firings and one `WINDOW_PRESENTED` row per build; an interval whose decisions or presentations were withheld or lost gets one `WINDOWS_UNRECORDED` row naming why. Older formats read both fields as not recorded.
- **Builds.** The decision taps and the presentation taps are two groups installed with the event-feed family; a group that fails to locate or construct is withheld by name (collector status `event_windows`) and leaves the rest of the family installed.
- **Not offered** options come from the recorded content minus the offered ones, and only when the content's option count equals the live event's.
- **Pictures** are recorded as the resolved key. The game then tries prefixed sprite variants that depend on the installed art; the viewer draws the key from current art like every other picture.
