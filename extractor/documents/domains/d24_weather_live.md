## Condensed knowledge



The claim that weather is not saved and therefore has no oracle is **wrong for
realized weather**, and it survived long enough to shape earlier design. The
melted save persists province weather scalars (temperature, water, snow, offsets)
and region weather values (temperature, next weather change, phenomenon flags,
`arctic_water`). Realized weather is save-checkable like any other domain.

Keep that separate from generative internals. The temperature formula, the RNG,
and phenomenon-name ordering are computed — reverse engineering work, not missing
save persistence. Treating them as a coverage gap misreads what the save holds.

### The gameplay weather state is the per-region phenomenon

Solved against `hoi4.exe 1.19.1.0.b49d` (SHA-256 `16022851…`), so the addresses
are stale; the structure, the validation method and the residuals are what carry.

The first attempt targeted temperature and failed, because temperature is a
derived display value and is not stored anywhere — an exhaustive negative,
confirmed twice. The re-target that worked went after the phenomenon state that
lockstep determinism actually requires. Found by walking MSVC RTTI in the
in-memory image rather than by value scanning, which is why there is no
value-ambiguity to rule out.

| Class | vtable RVA | Live instances |
|---|---|---|
| `CWeatherManager` | `0x2950AF0` | 1 (singleton) |
| `SWeatherPerRegion` | `0x2950AA0` | 305 = 304 regions + id-0 sentinel |
| `SWeatherPerProvince` | `0x2950A50` | 13,414 |
| `CWeatherTerrainModifier` | `0x2950A00` | 34 |

The production locator is `CGameState` from `u64[module_base+0x33048C0]`, then
`CWeatherManager` from `u64[CGameState+0x688]`. The vtable singleton scan is RE
fallback only, never the recorder path.

`CWeatherManager+0x40` is a `PdxVector {begin @ +0x40, u32 size @ +0x48 = 305,
u32 cap @ +0x4C}` holding 305 `SWeatherPerRegion` **inline by value** at stride
352 (`0x160`). The array is indexed by region id — `index == region_id` for
305/305 elements. `+0x08` is a ~269 MB per-province spatial vector and `+0x388` a
preallocated scratch grid; neither is the phenomenon array.

On `SWeatherPerRegion`: `region_id` at `+0x08`; a weather-cycle accumulator at
`+0x28` (present for clear and active regions alike — **not** the phenomenon);
the **phenomenon `u32` at `+0x78`**; active-flag bytes at `+0x5D` and `+0x75`
(`2` for every active region, `0` for clear); and two vectors populated only when
phenomenon >= 1 — `+0x58` holding 16-byte `SLocalWeatherPosition` records
`{u32 local_prov_idx, u32 0, i32 signed_offset, i32 sign}` (the moving fronts)
and `+0x70` pointing at weather-effect entities.

Observed distribution over regions 1..304: `0` = 168 (clear), `1` = 131,
`2` = 5 (region ids 75, 81, 84, 93, 178). Zero values outside `{0,1,2}`.

### Why the pin is trusted

Five independent checks, not one:

- **Anchors 5/5.** Regions 20, 129, 160, 292 read `0` and region 31 reads `1`,
  matching the tooltip and the province→region map (province 7250, the tooltip's
  rain province, is in region 31).
- **Independent in-memory cross-check, 305/305.** `phenomenon >= 1` iff the
  `+0x58`/`+0x70` begin pointer is a heap address. Two unrelated signals, zero
  disagreements.
- **Negative control.** Reading the same `+0x78` on the *geometry* class
  `CStrategicRegion` (vtable `0x29468B8`) yields a module-base pointer low-dword
  for 304/304 objects; 0/304 land in `{0,1,2}`. The offset is class-specific, not
  a generic small-int alias. `+0x78` is also distinct from `+0x5D` (131/305
  regions differ).
- **Pause stability.** Region-31 body byte-identical across a 2 s gap.
- **External corroboration.** The five `phenomenon == 2` regions have May
  climatology midpoints of 17.5–20.0 °C, all warmer than the 15.9 °C global mean,
  so `2` is **not** a cold phenomenon — consistent with heavy rain or storm, not
  snow. All five allow value 2 in their static climatology set for May.

An independent adversarial re-derivation reproduced every claim from scratch —
re-walking RTTI with a stricter `pSelf` self-reference check, relocating the
singleton, walking all 305 elements, and reproducing the exact distribution and
the negative control — rather than re-running the original reader.

### What is still open

The value→**name** mapping (is `1` light rain or rain; is `2` heavy rain or
storm) is a file-order hypothesis, not a string-table read. The numeric state pin
is confirmed; only the cosmetic label per integer is unproven. To settle it,
drive `set_weather` in a controlled single-player session and read `+0x78` per
phenomenon, or statically RE the `set_weather` console handler or
`CIsLightRain::Evaluate` to see which integer each predicate compares against.

Displayed temperature is reproducible only to climatology-midpoint accuracy
(± several °C), not the exact ±1 °C tooltip integer. Climatology (static game
files), the clock, and the phenomenon are all in hand; the missing input is the
lockstep RNG state and the daily-variation formula. That is a derived display
value, not gameplay state — the state the engine actually uses for combat and
movement modifiers is fully readable.

Per-province phenomenon was not mapped because per-region was sufficient;
`SWeatherPerProvince+0x08` is the province id and its `+0x58`/`+0x70` local
vectors are already visible if it is ever needed. Note that province 10167 shows
populated local-weather vectors while its region reads clear — local fronts
nearby, with the region field remaining gameplay-authoritative.
