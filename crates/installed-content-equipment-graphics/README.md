# installed-content-equipment-graphics

Equipment graphics pools, contexts, lookup identity and map/state joins. The implementation and its tests live in [`equipment_graphics`](src/equipment_graphics.rs); the same public paths are exported through `installed_content::equipment_graphics`. Shared parsing, identity and authored foundations come from [installed-content-core](../installed-content-core/README.md).

This reader also consumes [installed-content-states](../installed-content-states/README.md).

`Content::models` lists every model of every pool, in every bucket, whatever context or limit would visit it. [`aircraft`](src/equipment_graphics/aircraft.rs) builds the aircraft catalogue Fly mode picks from: every registered entity and bare `pdxmesh` of the registered descriptor roster, each with what makes it an aircraft's. That is a pool listing it under a plane type's key, its archetype, family or family's archetype; the airborne model ladder's name for a plane type's own, archetype, family or sprite key under any nonempty prefix; a recorded design's saved model of a plane type; or a registered clone relation to one of those (copies and what they copy, not siblings). A plane type is one the engine's plane classifier admits by its effective categories (`Database::category` against the engine's plane mask). A name a reference makes that nothing registers is listed, refused. `aircraft::refusal` is the roster-only reason a name cannot be flown, shared with the viewer's bake: a declaration it uses cannot be played (`Roster::refused_declaration`), it is an entity that draws nothing, or nothing registers it. An entity draws when it binds a registered mesh or attaches, at any depth, a registered entity that does; as in the model composer, an attachment child that no entity registers draws nothing, though a bare mesh can be flown itself. Unreadable descriptor files, registration logs, plane keys that are not text and recorded design types the content lacks are named and counted.

Resolve every authored input through the recorded `ResolvedLayers` content stack, including folders, archives, DLC, mods and replace_path. Preserve native order, lookup identity, duplicate handling, recovery and named/counted diagnostics. Keep evaluation and rendering in consumers.

## Tests

Synthetic tests live beside the reader. Integration tests of independent readers live in `installed-content`; layer fixtures come from the core through dev-dependencies. `test-support` forwards the existing core test constructors and retains reader test gating. Runtime metadata tests initialize `BATTLE_PLAN_GAME_DIR`; ignored installation tests remain read-only. See the [installed-content contracts](../installed-content/README.md) and [project rules](../../AGENTS.md).
