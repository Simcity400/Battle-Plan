# recorder-oracle-relations

Faction comparisons cover sparse account admission (current positive member or retained goal history), exact balances/gains/baselines/selections, variables, research member/bonus arrays, minimum upgrades, doctrine folders, saved projection effects and faction/system resource pools. Unsaved refresh totals, normalized shares, rank, scientist base and held goal progress/sections require the faction-screen integration comparison; no current-input substitute is used.

Country relations, opinions, faction membership and directed visibility joins. Owns [relations.rs](src/relations.rs) and its child tests. The [oracle command](../recorder-oracle/README.md) composes comparisons; this crate calls its specific dependent comparisons directly.

Faction goal comparisons project every recorded status owner and occurrence through the native save rules: full owner identity, manifest spelling, runtime status and date, history omission/order, nonzero signed slots and term dates. Missing goal tables or token spellings fail the comparison. The retained display-progress scalar has no saved equivalent and is identified as unsaved.

Research/manpower access, rules, shared programme references and manpower have separate comparison groups. Unlock bytes project nonzero to the save boolean, retaining missing-key differences. They preserve repeated tokens and full references in order; manpower uses the serializer's positive-value gate and authenticated country naming, including reserved raw zero. Missing tables and noncontiguous occurrence ordinals fail independently.

Table completeness, exact joins, differences and named limitations use [shared oracle support](../recorder-oracle-support/README.md). Content-dependent facts resolve through the recorded content stack. Synthetic fixtures are dev-only through the support crate's `test-support` feature.

Shared rules live in [AGENTS.md](../../AGENTS.md); the [recorder guide](../recorder/README.md) defines fresh-save/load and matched-native-observation checks.

`FactionAdvisorModifiers` compares every slot header, owner/advisor token, change-date presence and each independently owned nonzero modifier entry/name against the save. Character tokens join through lexical identity. Refresh results derive from their recorded supplying operands and boundaries; their unsaved native values remain explicit faction-screen integration checks.

Effective subject-contribution and population-growth accumulator operands are not independently serialized in faction accounts. The report names these limitations; integration compares the demanded getters and the contribution explanation at its explicitly labelled recruitment supplying hour.
